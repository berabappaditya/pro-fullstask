Caching, async, scheduling and events

Four annotations that remove plumbing: @Cacheable skips repeat work, @Async runs it on another thread, @Scheduled runs it on a timer, and application events decouple who-did-what from who-reacts.

In the franchise

The price of masala chai rarely changes, so the clerk keeps it on a sticky note instead of asking the owner every time (cache), and replaces the note when the price changes (evict). Sending the customer an SMS receipt is handed to a runner so the queue keeps moving (async). Every night at 2 am someone counts the stock (scheduled). When an order is paid, a bell rings and whoever cares reacts: kitchen, loyalty desk, accounts (events).

Same proxy rules

All four rely on proxies: self-invocation skips them, private methods are ignored. Plus: @Async loses the caller's ThreadLocals (SecurityContext, MDC, transaction), so pass what you need as arguments; a void @Async method's exception is only logged unless you configure an AsyncUncaughtExceptionHandler; @Cacheable keys must be stable and values serialisable for Redis.

Sticky note, runner, night shift, a bell.

@Cacheable skips on hit, @CachePut refreshes, @CacheEvict removes, always a TTL. @Async on a bounded pool. Cron = sec min hour day month weekday. AFTER_COMMIT listeners for side effects.

Interview questions

How do you keep a cache consistent with the database?

Cache-aside with TTL: read through @Cacheable, evict (not update) on writes after commit, keep TTLs short for changing data. Accept brief staleness, or for critical data skip caching. Beware stampedes on hot keys (Caffeine's refreshAfterWrite, locking or request coalescing). Details in the System Design book's caching chapter.

A @Scheduled job runs on every pod. How do you run it once?

Use a distributed lock (ShedLock with a DB/Redis lock table), a leader election, a dedicated single-replica worker deployment, or move it out to a platform scheduler (Kubernetes CronJob, Cloud Scheduler, EventBridge) that calls an endpoint or runs a job.
