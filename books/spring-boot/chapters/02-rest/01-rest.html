REST API basics: resources, methods and status codes

URLs name things (nouns), HTTP methods say what to do (verbs), status codes say what happened. Every request carries everything the server needs: stateless.

In the franchise

The menu board lists things: /orders, /orders/7. What you do with them is the verb: look (GET), place a new order (POST), replace your whole order (PUT), change only the sugar (PATCH), cancel (DELETE). The counter answers with a token colour: green "here you go" (200), "order placed" (201), red "we don't have that" (404).

Interview tip: design checklist

Plural nouns (/orders), nesting only for ownership (/orders/7/items), pagination on every list, an Idempotency-Key header for POSTs that move money, versioning (/api/v1 or a header; Boot 4 has built-in API versioning, see {{ref:ch-boot4}}), and a consistent error format (RFC 9457 ProblemDetail, {{ref:ch-errors}}).

Lock it in

Nouns in the URL, verbs in the method, outcome in the status.

GET/PUT/DELETE are idempotent, POST is not. 201 + Location for create, 204 for delete. 401 = who are you, 403 = not allowed.

Interview questions

PUT vs PATCH vs POST?

POST creates a new resource (server picks the id) and isn't idempotent. PUT replaces the full resource at a known URL; repeating it gives the same state. PATCH applies a partial change; it can be idempotent (set status = PAID) or not (add 1 item), depending on the patch.

What makes an API RESTful?

Resources identified by URIs, a uniform interface (standard methods and status codes), stateless requests, cacheable responses where appropriate, client–server separation and layered systems. HATEOAS (links in responses) is the strict final constraint, rarely used in practice.
