Exception handling: one place, one error format

Throw meaningful exceptions from the service; translate them to HTTP once, in a @RestControllerAdvice. Use RFC 9457 ProblemDetail as the response body.

In the franchise

When something goes wrong, the chef doesn't run to the customer. He sends a slip to the complaints desk, which has a standard apology card for each problem: "out of stock", "card declined", "kitchen closed". Customers always get the same, polite format, never the chef's shouting.

Common trap

Returning stack traces or SQL error text to clients leaks internals and helps attackers. Log the details with a correlation/trace id; return a clean message containing that id.

Lock it in

One complaints desk, one apology card format.

Throw domain exceptions → @RestControllerAdvice + @ExceptionHandler → ProblemDetail. Specific handlers first, Exception.class last.

Interview questions

@ControllerAdvice vs @RestControllerAdvice?

@RestControllerAdvice = @ControllerAdvice + @ResponseBody, so handler return values are written as the response body (JSON) rather than resolved as view names. Both apply globally (optionally narrowed by package or annotation).

@ResponseStatus on an exception vs @ExceptionHandler?

@ResponseStatus on the exception class maps it to a status with no body customisation. @ExceptionHandler gives full control over status, headers and body, and keeps HTTP knowledge out of domain exceptions. ResponseStatusException is a quick inline option.
