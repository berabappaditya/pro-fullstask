Configuration, properties and profiles

Same JAR, different settings per environment. Properties come from many sources with a clear precedence; bind groups of them into typed objects with @ConfigurationProperties.

In the franchise

Every branch gets the same kit, but the Kolkata branch sets the price list in rupees and opens at 6 am, while the airport branch opens 24 hours. The settings live on a card pinned inside the door (properties), not welded into the stove. A note from head office on the day (command-line argument) beats the card.

Where values come from (highest priority first)

  1. Command-line argumentsjava -jar app.jar --server.port=9090
  2. Environment variablesSERVER_PORT=9090, SPRING_DATASOURCE_URL=… (relaxed binding: dots → underscores, upper case). The usual way in Docker/Kubernetes.
  3. Profile-specific filesapplication-prod.yml when spring.profiles.active=prod
  4. application.properties / application.ymlin src/main/resources (or ./config/ next to the JAR, which wins over the packaged one)
  5. Defaultsin code: @Value("${x:default}"), field initialisers in properties classes.
Secrets

Never commit passwords or API keys in properties files. Inject them as environment variables from a secrets manager (AWS Secrets Manager, GCP Secret Manager, Vault, Kubernetes Secrets). See {{xref:cloud-devops/ch-cloud-security}}.

Lock it in

Same kit, a different card on each door.

Command line > env vars > profile file > application file > defaults. @ConfigurationProperties for groups, @Value for one-offs. Profiles: spring.profiles.active.

Interview questions

@Value vs @ConfigurationProperties?

@Value injects single values with SpEL support but no grouping, validation or metadata. @ConfigurationProperties binds a whole prefix to a typed object (records work well) with relaxed binding, validation, conversion (Duration, DataSize), IDE autocompletion via the configuration processor, and one place to see all settings.

How do you manage config across dev, test and prod?

One artifact; profile-specific files or blocks for non-secret differences; environment variables or a config server / secrets manager for secrets and per-environment values; ddl-auto none/validate in prod with Flyway or Liquibase migrations.
