Auto-configuration and starters: how Boot "just knows"

Boot reads a list of candidate configuration classes and keeps only those whose @Conditional checks pass: is this class on the classpath, is that bean missing, is this property set?

In the franchise

The kit has a rule book: "If the shop has a gas line, fit a gas stove. If the owner already brought their own stove, don't fit ours. If the owner ticked 'serve coffee', install the coffee machine." The installer reads the rules on opening day and fits only what applies. That's auto-configuration.

Interview questions

How does auto-configuration work internally?

@EnableAutoConfiguration imports AutoConfigurationImportSelector, which loads candidate classes from META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports in every jar (spring.factories before Boot 2.7/3). Each candidate is a @Configuration guarded by @Conditional annotations evaluated against the classpath, existing beans, properties and environment. Matching ones register their beans, after user configuration, so @ConditionalOnMissingBean lets user beans take precedence.

How would you write your own starter?

Create an autoconfigure module with an @AutoConfiguration class (conditions + @ConfigurationProperties), list it in the AutoConfiguration.imports file, and a starter module that depends on it plus the libraries. Name it acme-spring-boot-starter (only Spring's own starters use the spring-boot-starter-* prefix).
