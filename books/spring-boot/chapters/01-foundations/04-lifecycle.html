Bean lifecycle and scopes

Instantiate → inject → aware callbacks → BeanPostProcessors before → init (@PostConstruct) → BeanPostProcessors after (proxies!) → ready → @PreDestroy. Singleton is the default scope.

Singletons are shared by all threads

A singleton service handles every request concurrently. Never keep per-request state in its fields (private User currentUser; is a data leak between customers). Keep services stateless, or use thread-safe structures. See {{xref:java-core/ch-sync}}.

Interview questions

What is a BeanPostProcessor?

A hook that sees every bean before and after initialisation and can modify or replace it. Spring uses them to apply AOP: the after-init step wraps beans with @Transactional, @Async or @Cacheable in proxies. That's why the object injected into others is often a proxy, not your class.

Is a singleton bean thread-safe?

Not automatically. Singleton means one instance per container; many request threads call it at once. It's safe if it's stateless (only final, thread-safe dependencies). Mutable fields need synchronization or should be moved to method locals.

Why isn't @PreDestroy called on prototype beans?

The container hands prototype instances to the caller and doesn't track them afterwards, so it can't know when they're done. The caller must clean them up.
