Transactions: how @Transactional really works

A proxy opens a transaction before your method and commits or rolls back after it. Know the defaults: rollback on unchecked only, REQUIRED propagation, and no effect on self-invocation.

In the franchise

A customer pays and gets chai: both or neither. If the milk runs out after the payment, the cashier refunds (rollback). The manager's assistant (the proxy) stands at the door of every "@Transactional" room: opens the cash drawer when you walk in, closes it when you leave happily, refunds everything if you leave shouting. But if you walk from one room to another through the inside corridor (calling a method in the same class), the assistant never sees you.

The gotchas that appear in every interview

readOnly = true
For queries

Hibernate skips dirty checking and snapshots (less memory/CPU), and some drivers/routers send it to a read replica. Put it on the class, override on writes.

isolation
How much you see of others

READ_COMMITTED (Postgres default), REPEATABLE_READ (MySQL InnoDB default), SERIALIZABLE. See {{xref:system-design/ch-db}}.

timeout
Fail fast

timeout = 5 seconds: rolls back long-running transactions.

keep it short
No HTTP calls inside

A transaction holds a DB connection. Calling a slow API inside it exhausts the pool. Call out first, or use the outbox pattern.

Lock it in

The assistant guards the door, not the corridor.

Proxy-based: public methods, called from another bean. Rolls back on unchecked only. REQUIRED joins, REQUIRES_NEW suspends and starts fresh. Keep transactions short.

Interview questions

How does @Transactional work internally?

At startup a BeanPostProcessor wraps beans having @Transactional in a proxy (JDK dynamic proxy for interfaces or CGLIB subclass). On each call the TransactionInterceptor asks the PlatformTransactionManager (JpaTransactionManager) to begin or join a transaction based on propagation, binds the connection/EntityManager to the current thread (ThreadLocal), invokes the real method, then commits or rolls back according to the rollback rules.

REQUIRED vs REQUIRES_NEW, with a real use case.

REQUIRED joins the caller's transaction: if anything fails, everything rolls back together. REQUIRES_NEW suspends the caller and runs independently: its commit survives the caller's rollback. Use case: write an audit log or a "payment attempted" record that must persist even if the main business transaction rolls back. Beware: it uses a second connection.

Inner REQUIRED method throws, outer catches the exception. What happens?

The inner proxy marks the shared transaction rollback-only. The outer method continues, but on commit Spring finds it rollback-only and throws UnexpectedRollbackException; nothing is saved. Use REQUIRES_NEW (or NESTED) for the inner call if its failure should be isolated.
