Spring Data repositories: queries from method names

Declare an interface; Spring generates the implementation at startup. Method names become queries; @Query covers the rest; Pageable keeps lists bounded.

In the franchise

The storekeeper understands a fixed phrasebook: "find by name", "count by city", "find by price between … order by name". Say it in that form and he knows exactly which shelf to check. For anything unusual you hand him a written note (@Query).

Deep pages

OFFSET 100000 makes the database read and discard 100,000 rows. For infinite scroll or exports use keyset (cursor) pagination: WHERE id < :lastSeenId ORDER BY id DESC LIMIT 20 (Spring Data supports it with ScrollPosition / Window).

Derived methods for simple queries, @Query when the name gets long, @Modifying for updates, projections for read APIs, Pageable on every list.

Interview questions

save() vs saveAndFlush()? findById vs getReferenceById?

save() persists or merges and the SQL runs at flush/commit; saveAndFlush() forces the SQL immediately (useful to catch constraint violations now). findById queries and returns an Optional; getReferenceById returns a lazy proxy without a query (great for setting a foreign key: order.setCustomer(repo.getReferenceById(id))), throwing EntityNotFoundException only if accessed and missing.

Page vs Slice?

Page runs an extra COUNT query to know total elements/pages. Slice only fetches size+1 rows to know whether there's a next page: cheaper for "load more" UIs.
