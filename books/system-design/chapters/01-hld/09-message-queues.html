Message queues, pub/sub and Kafka

A message queue lets one part of a system drop off work and move on, while another part picks it up when it's ready. The two never have to wait for each other.

At Ramu's chai stall

At first, the cashier took an order, then stood waiting at the stove until the tea was ready, then served it. During rush hour the line didn't move. So Ramu put up a metal spike: the cashier writes an order slip, sticks it on the spike and immediately serves the next customer. Two cooks pull slips off the spike at their own pace.

At 8 a.m. the spike holds 40 slips. Nobody is turned away; the cooks just catch up by 8:20. The spike is a message queue. The cashier is the producer, the cooks are consumers, and the spike absorbing the rush is called load levelling.

Why queues are everywhere

Decoupling

The producer doesn't know or care who consumes. Add a new "SMS worker" without touching the order service.

Load levelling

Spikes queue up instead of crashing consumers. Consumers work at a steady, safe rate.

Reliability

If a consumer crashes, the message stays in the queue and is retried.

Scaling consumers

Queue growing? Add more workers. They share the messages.

Two shapes: queue and pub/sub

Point-to-point queue

Each message is handled by exactly one consumer, then deleted. Work distribution: "resize this image", "send this email". RabbitMQ queues, AWS SQS.

Publish / subscribe

Each message goes to every subscriber. Event broadcasting: "OrderPlaced" is heard by email, inventory and analytics. Kafka topics, SNS, Redis pub/sub.

Because at-least-once means duplicates will arrive, consumers must be idempotent: processing the same message twice must have the same effect as once.

Things that go wrong, and the standard fixes

Poison message

A message that always fails blocks or loops forever. After N retries, move it to a dead-letter queue (DLQ) for humans to inspect.

Ordering

Only guaranteed per partition/queue. Use the entity ID (orderId) as the key so its events stay in order.

Backpressure

Consumers falling behind forever? Monitor consumer lag; scale consumers (up to the partition count) or slow producers.

Dual write

Saving to the DB and publishing to Kafka are two systems; one can fail. Use the transactional outbox ({{ref:ch-dtx}}).

Queue = one consumer per message. Pub/sub = every subscriber gets it. Kafka = partitioned log, ordered per partition, replayable. Assume at-least-once, so make consumers idempotent, and send poison messages to a DLQ.

Interview questions

How many consumers can usefully read a Kafka topic with 6 partitions in one group?

At most 6. Each partition is assigned to exactly one consumer in a group; a 7th consumer sits idle. To scale beyond that, increase partitions (plan this upfront, since changing partition count reshuffles key-to-partition mapping).

When would you not use a queue?

When the user needs the result right now (checking a password, reading a balance), when strict request–response semantics are needed, or when the added infrastructure and eventual consistency aren't worth it for a small system.
