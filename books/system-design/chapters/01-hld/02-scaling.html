Scaling: bigger machine or more machines?

Scalability is the ability to handle more load by adding resources. You either buy a bigger machine (scale up) or add more machines (scale out).

At Ramu's chai stall

With 2,000 customers a day, Ramu has two choices. Option A: buy a giant 50-litre kettle and a faster stove. Simple, but there's a limit to how big a kettle gets, it's expensive, and if that one stove breaks, nobody gets tea. Option B: open three more identical stalls next to each other, each with an ordinary kettle. More to coordinate, but he can keep adding stalls, and if one breaks the others keep serving.

Option A is vertical scaling. Option B is horizontal scaling.

Vertical (scale up)Horizontal (scale out)
HowMore CPU, RAM, faster disk on the same machineMore machines sharing the work
LimitHard ceiling: the biggest machine money can buyPractically unlimited
FailureSingle point of failureOne machine dies, others continue
ComplexityVery low; no code changesNeeds load balancing, stateless code, distributed data
Cost curveGets expensive fast at the top endRoughly linear with commodity hardware
Good forEarly stage, relational DB primary, quick fixWeb/app tiers, big data, anything that must stay up

The catch: servers must be stateless

Ramu remembers that Priya takes less sugar. When there are four stalls, Priya might go to stall 3 tomorrow, and stall 3 has never met her. If each stall keeps its own memory, customers get inconsistent service.

Latency vs throughput

Latency: how long one trip takes

Time from request to response, in milliseconds. "My chai arrived in 2 minutes."

Throughput: how many per second

Requests (or bytes) handled per unit of time. "The stall serves 600 cups an hour."

Think of a highway: the speed limit is latency, the number of lanes is throughput. Adding lanes (more servers) raises throughput but doesn't make one car faster. Caching and better algorithms reduce latency.

Measure latency with percentiles, not averages. p50 (median) = half the requests are faster than this. p99 = 99% are faster; the slowest 1% are slower. If your p50 is 80 ms but p99 is 4 seconds, 1 in 100 users is having a terrible time, and the average hides it.

Lock it in

Memory is a minute, disk is a day, the network is a voyage.

RAM is ~1000× faster than SSD; crossing the planet is slower than everything. That is why we cache in memory, avoid chatty network calls, and put data near users. Scale up first when it's cheap; scale out when you need no ceiling and no single point of failure. Scale-out needs stateless servers.

Interview questions

Your single server is at 90% CPU. What do you do?

First find out why (profiling, slow queries, missing cache). Short term, scaling up is the fastest fix. Long term, make the app stateless, put a load balancer in front and scale horizontally, with auto-scaling based on CPU or request rate. Also look at caching hot reads so less work reaches the server at all.

Why are percentiles better than averages for latency?

Latency distributions have long tails. A few very slow requests barely move the average but hurt real users, and in a microservice call chain the slowest dependency decides the total. p95/p99 expose the tail, so SLOs are written in percentiles.
