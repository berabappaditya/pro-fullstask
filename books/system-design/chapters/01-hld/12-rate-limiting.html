Rate limiting

A rate limiter caps how many requests a client may make in a period of time, protecting the system from abuse, accidents and overload.

At Ramu's chai stall

A reseller starts buying 200 cups at a time and selling them outside the station at double the price. Regular customers find the flasks empty. Ramu puts up a sign: "Maximum 5 cups per person per 10 minutes." Bablu at the gate gives each person 5 tokens; every cup costs a token; tokens come back slowly over time. When you're out of tokens, you wait.

That's the token bucket algorithm, the most widely used rate limiter.

Why rate limit?

Stop abuse

Brute-force logins, scraping, DDoS.

Fairness

One noisy tenant can't starve everyone else.

Protect downstream

Your DB or a paid third-party API can only take so much.

Cost control

Free tier = 100 calls/day; paid tier = more.

Distributed rate limiting

With 20 API servers, each keeping its own bucket, a user could get 20× the limit. Keep counters in Redis, shared by all servers, and make the check-and-increment atomic with a Lua script (or INCR + EXPIRE for a fixed window).

Interview tip

Say where the limiter lives (API gateway is typical), what key it limits by (user ID, API key, IP for anonymous traffic), what happens on reject (429 + Retry-After), and what happens if Redis is down (usually fail open: allow traffic rather than block every user).

Lock it in

Tokens drip in, requests spend them.

Token bucket = bursts OK, average capped. Leaky bucket = smooth output. Fixed window = simple but edge bursts. Sliding window = accurate. Share counters in Redis with atomic ops across servers.

Interview questions

Design a rate limiter for an API used by 10 million users.

Put it in the API gateway as middleware. Rules (per user/API key/endpoint) come from a config store and are cached locally. Counters live in a Redis cluster sharded by key; use a token bucket or sliding window counter via an atomic Lua script. Return 429 with Retry-After and rate-limit headers. For latency, consider a small local pre-check and async syncing for non-critical limits. Monitor rejected counts; fail open if Redis is unreachable.

What's the fixed-window edge problem?

A limit of 100/minute resets at each minute boundary, so a client can send 100 requests at 12:00:59 and another 100 at 12:01:00, i.e. 200 within two seconds. Sliding windows fix this.
