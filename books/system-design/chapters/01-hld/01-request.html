How a request travels

A client asks, a server answers. Everything else in this book is about making that conversation fast, reliable and able to happen millions of times a second.

At Ramu's chai stall

A tourist steps off the train and wants Ramu's famous chai. She doesn't know where the stall is, so she asks the station porter, who knows every shop's location. He says "Platform 2, next to the bookshop." She walks over, says "One elaichi chai, less sugar," pays, and gets her cup.

Map it: the tourist is the client, the porter is DNS (turns a name into an address), the walk is the network, "one elaichi chai" is the request, Ramu is the server, and the cup of tea is the response.

Definition

Client–server model: a client (browser, mobile app, another service) sends a request over the network to a server, which processes it and sends back a response. The server waits for requests; the client starts the conversation.

What happens when you type a URL and press Enter

This is the single most common warm-up question in interviews. Here is the full journey for https://www.ramuchai.in/menu:

  1. DNS lookupThe browser checks its cache, then the OS, then asks a DNS resolver. The resolver walks the hierarchy: root → .in TLD → the domain's authoritative name server, which returns the IP address.
  2. TCP connectionThree-way handshake: client sends SYN, server replies SYN-ACK, client sends ACK. Now there is a reliable pipe.
  3. TLS handshake (for HTTPS)Server proves its identity with a certificate; both sides agree on encryption keys. From now on, everything is encrypted.
  4. HTTP requestThe browser sends GET /menu with headers (cookies, accepted formats, user agent).
  5. Server workA load balancer may forward it to one app server, which runs business logic, hits a cache or database and builds a response.
  6. HTTP responseStatus code, headers and body (HTML or JSON) come back.
  7. RenderingThe browser parses HTML, fetches CSS, JS and images (often from a CDN), and paints the page.

TCP vs UDP

TCP: registered post

Connection first, then every packet is numbered, acknowledged and resent if lost. Arrives complete and in order. Used by HTTP/1.1, HTTP/2, databases, email.

UDP: shouting across the room

No connection, no guarantee. Some words may be lost, but it's very fast. Used for video calls, online games, DNS queries, and HTTP/3 (QUIC builds reliability on top of UDP).

In plain words

An IP address is a building's street address. A port is the flat number inside it (443 for HTTPS, 3306 for MySQL, 6379 for Redis). DNS is the phone book that turns "ramuchai.in" into the street address. HTTP is the language the visitor and the shopkeeper agree to speak.

DNS → TCP → TLS → HTTP request → Response → Render. And remember: HTTP is stateless; each request carries everything the server needs (cookies, tokens) because the server doesn't remember the previous one.

Interview questions

Why is HTTP called stateless, and how do websites remember that I'm logged in?

Each HTTP request is independent; the protocol has no memory of earlier requests. Websites add state on top: after login the server gives you a session ID cookie (pointing at session data stored on the server or in Redis) or a signed token like a JWT. Your browser sends it with every request, so the server can recognise you again.

What's the difference between 401 and 403?

401 Unauthorized really means unauthenticated: "I don't know who you are; log in." 403 Forbidden means "I know who you are, but you're not allowed to do this."

Where can DNS be used for system design, not just name lookup?

DNS can return different IPs to different users: round-robin across servers, the nearest data centre (geo-DNS), or a healthy region during failover. Its weakness is caching: clients may keep an old IP until the TTL expires, so DNS failover is slow compared with a load balancer.
