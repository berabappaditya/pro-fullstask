The HLD interview framework

A system design interview is a guided conversation, not a quiz. A fixed sequence of steps keeps you calm and makes sure you cover what interviewers grade.

At Ramu's chai stall

When a hotel asks Ramu to run its breakfast tea service, he doesn't start buying kettles. He asks: How many guests? What time? Only tea, or coffee too? Any VIP floor? Then he estimates, sketches the setup (one central boiler, three serving points, a runner), and only then worries about details like what happens if the boiler fails. Ask, estimate, sketch, deepen.

  1. Clarify requirementsFunctional: what must users be able to do? Pick 3–4 core features and say what's out of scope. Non-functional: scale (users, data), latency targets, availability, consistency needs, read/write ratio, geography.
  2. EstimateQPS (average and peak), storage over 5 years, bandwidth, cache size ({{ref:ch-estimate}}). Conclude: "read-heavy, so…".
  3. Define the API and data model3–5 endpoints with parameters. Main entities, keys and which database type, justified by access patterns.
  4. Draw the high-level designClient → (CDN) → LB → services → cache → DB, plus queues and workers. Walk through one write and one read request end to end.
  5. Deep-diveThe interviewer will steer you, or you pick the hardest parts: the ID scheme, the feed fan-out, sharding key, consistency of payments, hot keys, failure handling.
  6. Wrap upName bottlenecks and single points of failure, how you'd monitor it, and what you'd do at 10× scale.

Non-functional checklist

Scale

DAU, QPS, data volume, growth rate.

Performance

Latency targets (p99), real-time needs.

Availability

How many nines; multi-region?

Consistency

Strong (money) or eventual (likes)?

Durability

Can we ever lose data?

Security & compliance

Auth, PII, data residency.

Phrases that signal seniority

"The trade-off here is…"

Every choice costs something. Name it.

"Given it's read-heavy, I'd…"

Tie decisions back to the requirements and numbers.

"Let's start simple, then scale."

A single-server version first, then evolve it.

"If this component fails…"

Proactively discuss failure modes.

Common trap

Jumping into Kafka, Kubernetes and sharding in minute two, before knowing the scale. Or staying silent while drawing. Or going deep on one component and never finishing the end-to-end picture. Breadth first, then depth.
