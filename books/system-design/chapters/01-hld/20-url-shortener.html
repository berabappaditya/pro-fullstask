Case study: design a URL shortener

Turn a long URL into a short code like chai.ly/aZ3kP9q and redirect anyone who opens it. The most common first HLD question, walked through with the framework.

Step 1 · Requirements

Functional
  • Create a short URL for a long URL
  • Redirect short → long
  • Optional custom alias and expiry
  • Click analytics (counts)
Non-functional
  • Very low redirect latency (< 50 ms)
  • Highly available: broken links are unacceptable
  • Codes not guessable in sequence
  • Read-heavy (~100 reads per write)

Step 2 · Estimation

QuantityWorkingResult
New URLs10M/day ÷ 105~100 writes/s
Redirects100 × writes = 1B/day ÷ 105~10,000 reads/s (peak ~30K)
Storage10M × 500 B × 365 × 5 years~9 TB over 5 years
Code lengthBase62 (a–z, A–Z, 0–9): 627≈ 3.5 trillion codes: 7 chars is plenty
Cache20% of daily hot links: 0.2 × 1B reads hit ~few M URLs × 500 Ba few GB in Redis

Step 3 · API and data model

301 or 302? 301 (permanent) lets browsers cache the redirect, which saves load but hides repeat clicks from analytics. 302 (temporary) sends every click through you, so analytics are accurate. Most shorteners with analytics use 302.

Data model: one main table, accessed purely by key. A key-value / wide-column store (DynamoDB, Cassandra) or sharded MySQL keyed by code both work.

Step 5 · Deep dive: generating the short code

ApproachHowProsCons
Hash the URLMD5/SHA-256 of the long URL, take first 7 base62 charsSame URL → same code (dedup)Collisions: must check DB and re-hash; the extra read costs latency
Counter + Base62Unique numeric ID (Snowflake, or a DB/ZooKeeper range allocator) → encode in base62No collisions, ever; short codesSequential codes are guessable (scramble with a bijective shuffle); needs a reliable ID source
Pre-generated keys (KGS)A service pre-creates random unused codes and hands out batchesFast, random, collision-freeExtra service; must not hand the same batch to two servers

A solid answer: range-based counter. Each shorten-service instance asks the KGS for a block of 1,000 IDs (e.g. 5,000,000–5,000,999), uses them from memory, and asks again when it runs out. No coordination per request; a crash just wastes the rest of a block.

Other deep dives worth mentioning

Caching

Links follow a power law: a few go viral. Cache-aside in Redis with LRU; most redirects never touch the DB.

Custom aliases

Insert with a uniqueness check (conditional put / unique key); reject if taken.

Expiry

Check expires_at on read (lazy), plus a background job to delete expired rows. Use DB TTL if supported.

Abuse

Rate-limit creation per user/IP; scan long URLs against malware lists.

Availability

Replicate the DB across zones; the redirect path depends only on cache + DB read replicas.

Analytics

Click events → Kafka → aggregators → a columnar store (ClickHouse). Never on the redirect's critical path.

Lock it in

7 chars of Base62, counter in ranges, cache the hot links, 302 for analytics.

Read-heavy (100:1) → separate read path, aggressive caching. Codes from a collision-free ID source + Base62. Analytics asynchronously through a queue.
