Sharding and consistent hashing

Sharding splits one big dataset into smaller pieces stored on different machines, so writes and storage can grow beyond what one database can hold.

At Ramu's chai stall

The head-office ledger is now 4,000 pages, and only one clerk can write in it at a time. The queue of clerks waiting to write is longer than the queue of customers. Ramu splits it into three ledgers: surnames A–H, I–P and Q–Z, each with its own clerk. Three clerks now write in parallel.

But then a hundred customers named "Sharma" and "Singh" show up, and the Q–Z clerk is drowning while A–H sits idle. That's a hot shard, and it's why choosing the split (the shard key) is the most important sharding decision.

What sharding costs you

Cross-shard queries

"Top 10 customers overall" must ask every shard and merge (scatter–gather).

Cross-shard transactions

No simple ACID across shards. You need sagas or 2PC ({{ref:ch-dtx}}).

No cross-shard JOINs

Denormalise, or join in application code.

Resharding

Growing from 4 to 8 shards means moving data live without downtime.

Interview tip

Pick the shard key from the main access pattern. For a chat app: conversation_id, so one conversation's messages live together. For an e-commerce order system: customer_id, so "my orders" hits one shard. Say why, and name the hot-key risk (a celebrity, a giant tenant).

Consistent hashing, drawn

With plain hash(key) % N, going from 4 servers to 5 changes the answer for roughly 80% of keys. Every cache misses at once. Consistent hashing fixes this:

  1. Make a ringImagine hash values 0 … 2³²−1 bent into a circle.
  2. Place serversHash each server's name to a point on the ring.
  3. Place keysHash each key to a point, then walk clockwise to the first server. That server owns the key.
  4. Add a serverIt takes over only the keys between itself and its counter-clockwise neighbour. Everyone else stays put.
  5. Use virtual nodesPlace each physical server at 100–200 points on the ring so the slices are even and a removed server's load spreads over many servers, not one.
LiveConsistent hashing ring vs modulo hashing

60 keys are placed on the ring. Each key takes the colour of the server that owns it. When you add or remove a server, compare how many keys moved on the ring with how many would have moved using hash % N.

Used by: Cassandra and DynamoDB (partitioning), Memcached clients, Discord, Akamai, load balancers doing cache-friendly routing.

Shard when one machine can't hold the writes or the data. Choose the shard key from the main query. Hash for even spread, range for range queries, consistent hashing so adding a node moves only ~1/N keys, virtual nodes for balance.

Interview questions

Partitioning vs sharding vs replication?

Partitioning is splitting data into pieces; when the pieces live on different machines it's usually called sharding (horizontal partitioning). Vertical partitioning splits by columns or by feature (user profile table vs user activity table). Replication copies the same piece to multiple machines. Real systems do both: each shard has its own replicas.

How would you reshard a live MySQL database from 4 to 8 shards?

Use logical shards: hash keys into, say, 1,024 virtual buckets mapped to 4 physical servers. To grow, move whole buckets: copy a bucket's data to the new server, stream ongoing changes (binlog/CDC) until caught up, briefly block writes for that bucket, flip the mapping, then delete the old copy. Tools like Vitess automate this.
