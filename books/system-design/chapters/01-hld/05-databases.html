Databases: SQL, NoSQL, ACID and indexes

The database is the source of truth. Choosing the right kind, and using transactions and indexes well, decides whether your data is correct and fast.

At Ramu's chai stall

Ramu keeps a big ledger: customers on one page, orders on another, stock on a third, all with neat columns and cross-references ("Order 512 → Customer 88"). That's a relational (SQL) database.

His nephew runs the Instagram page and just throws each customer's whole story into one folder: name, photos, favourite drinks, comments, all together, every folder shaped a little differently. That's a document (NoSQL) database. Both work. They suit different jobs.

SQL vs NoSQL

SQL (relational)NoSQL (non-relational)
Shape of dataTables with fixed columns; rows linked by foreign keysDocuments, key-value pairs, wide columns or graphs; flexible schema
Query powerRich: JOINs, aggregations, ad-hoc SQLUsually by key or a few fields; JOINs limited or absent
GuaranteesACID transactionsOften BASE (eventual consistency); many now offer ACID per document or more
ScalingScales up easily; scaling out (sharding) is manual workBuilt to scale out across many nodes
ExamplesMySQL, PostgreSQL, Oracle, SQL ServerMongoDB, Cassandra, DynamoDB, Redis, Neo4j
Pick whenRelationships matter, correctness matters (payments, orders, inventory)Huge scale, flexible/changing shape, simple access patterns (logs, feeds, sessions, IoT)

The four families of NoSQL

key → value
Key-value

A giant hash map. Fastest possible lookups by key.

  • Redis, DynamoDB, Riak
  • Sessions, caches, carts
JSON docs
Document

Self-contained JSON-like documents; query on fields inside.

  • MongoDB, Couchbase, Firestore
  • Catalogues, profiles, CMS
row key → many columns
Wide-column

Rows with huge numbers of columns, partitioned across nodes; very fast writes.

  • Cassandra, HBase, Bigtable
  • Messages, time series, activity logs
nodes + edges
Graph

Relationships are first-class; walking connections is cheap.

  • Neo4j, Amazon Neptune
  • Social graphs, recommendations, fraud rings

Specialists you'll also name in designs: search engines (Elasticsearch, inverted index for full-text search), time-series DBs (InfluxDB, Prometheus), and object stores (S3, for files and blobs).

ACID: the promise of a transaction

A transaction is a group of operations that must succeed or fail together. Example: Priya pays ₹15 by wallet. Two things must happen: her wallet goes down by 15, Ramu's goes up by 15.

A
Atomicity: all or nothing

If the server crashes after debiting Priya but before crediting Ramu, the debit is rolled back. Money never vanishes.

C
Consistency: rules always hold

Constraints (balance ≥ 0, foreign keys, unique email) are true before and after every transaction.

I
Isolation: no peeking at half-done work

Two payments running at once behave as if they ran one after another.

D
Durability: committed means saved

Once the DB says "committed", a power cut won't lose it (write-ahead log on disk).

BASE is the looser NoSQL promise: Basically Available, Soft state, Eventually consistent. Replicas may disagree for a moment but converge.

Dirty read: you see another transaction's uncommitted change. Non-repeatable read: you read the same row twice and get different values. Phantom: you run the same query twice and new rows appear.

Optimistic vs pessimistic locking

Optimistic: "conflicts are rare"

No lock. Read a version number; on update, WHERE version = ?. If someone else changed it, fail and retry. Great for low contention (profile edits).

Pessimistic: "conflicts are likely"

Lock the row while working: SELECT … FOR UPDATE. Others wait. Good for hot rows (last seat on a flight, flash-sale stock).

Indexes: the back-of-the-book index

Finding "Priya" in a 10-million-row table without an index means reading every row (a full table scan). An index is a sorted structure, usually a B+ tree, that points straight to the right rows, the way a book's index points to page numbers.

Common trap

Indexes are not free. Every INSERT/UPDATE must update every index too, and indexes use disk and memory. Index the columns you filter, join and sort on; don't index everything. Low-cardinality columns (gender, boolean flags) alone are usually poor indexes.

Normalise or denormalise?

Normalised

Each fact stored once (customer name lives only in customers). No update anomalies; needs JOINs to read. Default for OLTP systems.

Denormalised

Copy data where it's read (store customer_name inside each order). Fast reads, no JOINs; must keep copies in sync. Common at scale and in NoSQL.

Lock it in

ACID = "All Conditions Isolated, Durable."

SQL when relationships and correctness rule; NoSQL when scale and flexible shape rule. Indexes turn scans into lookups at the cost of slower writes. Use optimistic locking for rare conflicts, pessimistic for hot rows.

Interview questions

How do you choose between SQL and NoSQL for a new feature?

Start from access patterns and guarantees. Need multi-row transactions, joins, ad-hoc reporting, strict integrity? SQL. Need massive write throughput, horizontal scale, a schema that changes often, and access mostly by key? NoSQL. Many systems use both: MySQL for orders and payments, Cassandra for activity logs, Redis for sessions, Elasticsearch for search ("polyglot persistence").

Why can adding an index make a system slower?

Writes must maintain every index, so write-heavy tables slow down; indexes consume buffer-pool memory, pushing hot data out; and the optimiser might pick a poor index. Measure with EXPLAIN and real workloads.

What does @Transactional not protect you from?

Self-invocation (calling a @Transactional method from the same class bypasses the Spring proxy), checked exceptions (no rollback by default), calls to other services or message brokers (those aren't in the DB transaction), and lost updates under the default isolation level unless you add locking.
