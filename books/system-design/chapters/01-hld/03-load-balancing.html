Load balancing

A load balancer sits in front of many servers and decides which one handles each request, so no single server is overloaded and dead servers are skipped.

At Ramu's chai stall

Four stalls now stand side by side, but everybody crowds stall 1 because it's nearest the station exit. Ramu hires his cousin Bablu to stand at the entrance and point: "You, stall 2. You, stall 3." Bablu also notices when stall 4's stove goes out and stops sending people there until it's fixed.

Bablu is the load balancer. Pointing people in turn is an algorithm. Checking the stoves is a health check.

What a load balancer gives you

Spreads load

No server is idle while another melts.

Hides failures

Health checks pull dead servers out of rotation.

Zero-downtime deploys

Drain one server, update it, put it back, repeat.

One front door

TLS termination, a single domain, easy to add servers behind it.

Algorithms: how the LB picks a server

static
Round robin

1, 2, 3, 1, 2, 3… Simple and fair when servers and requests are alike.

static
Weighted round robin

A server twice as big gets twice the turns. Good for mixed hardware.

dynamic
Least connections

Send to whoever is busiest the least. Best when requests take very different times.

dynamic
Least response time

Pick the server answering fastest right now.

hash
IP hash / consistent hash

hash(clientIP) % N: the same user always lands on the same server. Useful for caches and sticky behaviour.

random
Random / power of two choices

Pick two servers at random, use the less loaded one. Surprisingly close to optimal.

Real config: Nginx as a load balancer

Sticky sessions, and who balances the balancer?

Sticky sessions pin a user to one server (via a cookie). It's a quick fix for stateful apps but it breaks even spreading, and the user loses their session when that server dies. Prefer stateless servers ({{ref:ch-scaling}}).

A single load balancer is itself a single point of failure. Production setups run two in an active–passive pair sharing a floating virtual IP (keepalived/VRRP), or use a managed LB (AWS ALB) that is already redundant across zones. Across regions, DNS / global server load balancing sends users to the nearest healthy region.

Common trap

Health checks that only check "is the process alive" (/ping returns 200) miss servers that are alive but broken, e.g. lost their DB connection. A good /health checks critical dependencies, but keep it cheap, or the health checks themselves become load.

Lock it in

Bablu at the gate: Spread, Skip the sick, Single front door.

L4 = fast, sees only addresses. L7 = smart, sees URLs and headers. Least-connections when requests vary in length, round robin when they don't, hashing when the same user must land on the same server.

Interview questions

How does a load balancer know a server is down?

Active health checks: it calls /health every few seconds and removes the server after N failures, then re-adds it after M successes. Passive checks: it watches real traffic and marks a server bad after repeated errors or timeouts. Most setups use both.

Where would you put load balancers in a three-tier system?

Between users and web servers, between web/API servers and internal services, and sometimes in front of database read replicas. Each tier then scales independently.

Why is hash(key) % N a problem when N changes?

Changing N (adding or removing a server) remaps almost every key, so caches miss and sessions move all at once. Consistent hashing ({{ref:ch-sharding}}) fixes this by remapping only about 1/N of the keys.
