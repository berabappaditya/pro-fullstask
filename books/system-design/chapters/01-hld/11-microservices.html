Monolith vs microservices

A monolith is one deployable app that does everything; microservices split it into small services, each owning one business capability and its own data.

At Ramu's chai stall

In the original stall, Ramu did everything at one counter: tea, samosas, billing, deliveries. Easy to manage, one place to look. But when the samosa fryer catches fire, the whole stall shuts. And hiring a samosa specialist means retraining him on tea and billing too.

The flagship store now has separate counters: a tea counter, a snacks counter, a billing counter and a delivery desk. Each has its own staff, its own stock and its own hours. If snacks close, tea keeps selling. A front desk greets everyone and sends them to the right counter. That front desk is the API gateway.

The supporting cast of a microservice system

API Gateway

Single entry: routing, auth, rate limiting, TLS, request aggregation. Spring Cloud Gateway, Kong, AWS API Gateway.

Service discovery

Services register where they run; others look them up by name, not IP. Eureka, Consul, Kubernetes DNS.

Config server

Central, versioned configuration and secrets. Spring Cloud Config, Vault.

Service mesh

A sidecar proxy next to each service handles retries, mTLS and metrics without code changes. Istio, Linkerd.

Backend for Frontend

A thin API per client type (mobile BFF, web BFF) shaping data for that UI.

Observability

Centralised logs, metrics and distributed traces with a correlation ID across services ({{ref:ch-observe}}).

Common trap

The distributed monolith: services that share one database or must all deploy together. You get all the pain of microservices and none of the benefits. Also, splitting too early: start with a well-structured modular monolith and extract services along clear domain boundaries (DDD bounded contexts) when a team or scaling need justifies it.

Lock it in

Separate counters, separate stock, one front desk.

Microservice = one business capability, own data, independent deploy. Pay for it with network calls, eventual consistency and ops tooling. Monolith first is not a failure; it's usually the right start.

Interview questions

How do you decide service boundaries?

Follow business domains (Domain-Driven Design bounded contexts): Orders, Payments, Catalogue, Shipping. A good service has high cohesion inside, few calls outside, owns its data, and can be owned by one team. If two services always change together or need constant synchronous chatter, they probably belong together.

Sync (REST/gRPC) or async (events) between services?

Use sync when the caller needs an answer to continue (check stock before showing checkout). Use async events for side effects and for spreading information (OrderPlaced → email, analytics, loyalty). Async reduces coupling and cascading failures; sync is simpler to reason about. Most systems mix both.
