Distributed transactions: 2PC, Saga, Outbox, CQRS

When one business action touches several services or databases, you can't use a single ACID transaction. These patterns keep the overall result correct anyway.

At Ramu's chai stall

A wedding party orders: 500 cups of tea from Ramu, sweets from Mishra Sweets, and chairs from the tent house. It must be all or nothing; tea without chairs is useless.

Plan A, the strict planner: calls all three, "Can you reserve for Saturday? Don't confirm yet." When all three say yes, he calls again, "Confirm." If any says no, he tells everyone "Cancel." That's two-phase commit. But if the planner's phone dies between the calls, everyone waits, holding stock, unsure.

Plan B, the practical planner: books tea (done), books sweets (done), tries chairs (fails), then calls Mishra and Ramu to undo their bookings. That's a saga with compensating actions.

Two-phase commit (2PC)

Saga: a chain of local transactions with undo steps

StepServiceActionCompensation (undo)
1OrderCreate order (PENDING)Mark order CANCELLED
2PaymentCharge ₹500Refund ₹500
3InventoryReserve 500 cups of stockRelease stock
4DeliveryAssign a delivery slotFree the slot
5OrderMark order CONFIRMED(final step, nothing to undo)

If step 4 fails, run compensations backwards: release stock (3), refund (2), cancel order (1).

Transactional outbox: never lose an event

Common bug: save the order to MySQL, then publish OrderCreated to Kafka. If the app crashes between the two, the order exists but nobody hears about it. Or Kafka succeeds and the DB commit fails, and everyone hears about an order that doesn't exist.

CQRS and event sourcing

CQRS
Command Query Responsibility Segregation

Use one model for writes (normalised, validated) and a different, denormalised model for reads (e.g. an Elasticsearch index or a pre-joined table), kept in sync by events. Great when reads and writes look very different or scale very differently.

Event sourcing
Store the history, not the state

Like a bank passbook: you store every event (Deposited 500, Withdrew 200) and compute the balance by replaying. Full audit trail and time travel; harder queries and schema evolution. Often paired with CQRS.

Lock it in

2PC asks "ready?" then "go!". Saga does, then undoes.

Microservices default to sagas (eventual consistency + compensations), the outbox to publish events reliably, and idempotent consumers. 2PC only where strong atomicity across a few tightly coupled DBs is essential.

Interview questions

What's the weakness of sagas compared with ACID?

No isolation: other transactions can see intermediate states (order PENDING, payment taken, stock not yet reserved). You handle this with semantic locks (a PENDING status others respect), commutative updates, re-reading values, and designing compensations carefully, since some actions (a sent email) can't be undone, only followed by a correction.

When is CQRS overkill?

For simple CRUD where reads and writes use the same shape and modest scale. CQRS adds eventual consistency between the write and read models, more infrastructure and more code. Use it when read patterns are complex or much heavier than writes.
