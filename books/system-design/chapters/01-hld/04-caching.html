Caching and CDNs

A cache keeps a copy of frequently used data somewhere faster and closer, so you don't redo slow work for every request.

At Ramu's chai stall

Brewing each cup from scratch takes 4 minutes. But 80% of customers order the same plain masala chai. So every morning Ramu brews a big batch and keeps it hot in flasks on the counter. A masala chai order is now served in 10 seconds. Rare orders (green tea with honey) are still made fresh.

The flasks are a cache. Finding chai in the flask is a cache hit; having to brew is a cache miss. Throwing out tea older than 2 hours is a TTL (time to live). When the flask shelf is full and he removes the flavour nobody ordered recently, that's LRU eviction.

Caching strategies: who updates the cache, and when

StrategyHow it worksGoodBad
Cache-asideApp reads cache; on miss reads DB and fills cacheSimple; cache failure isn't fatal; only hot data cachedFirst request is slow; data can be stale until TTL
Read-throughCache itself loads from DB on missApp code is simplerNeeds a cache library/provider that supports it
Write-throughEvery write goes to cache and DB togetherCache always freshSlower writes; caches data nobody reads
Write-behind (write-back)Write to cache now, flush to DB later in batchesVery fast writesData loss if cache dies before flushing
Write-aroundWrite only to DB; cache fills on next readAvoids filling cache with write-once dataRecent writes miss the cache

Spring shortcut: the same thing with annotations is @Cacheable("menu") on getMenu and @CacheEvict("menu") on updateMenu, with Redis configured as the cache manager.

Eviction: what to throw out when the cache is full

LRU: Least Recently Used

Remove what hasn't been touched for the longest time. The default choice.

LFU: Least Frequently Used

Remove what's used least often. Good when popularity is stable.

FIFO

Remove the oldest inserted item, regardless of use. Simple, rarely best.

TTL

Every entry expires after a fixed time. Controls staleness rather than space.

Most recent → least recent

LRU is also a classic LLD coding question. The trick: a HashMap for O(1) lookup plus a doubly linked list for O(1) "move to front" and "remove last".

The four classic cache disasters

Stampede (thundering herd)

A hot key expires; 5,000 requests miss at once and all hit the DB.

  • Fix: lock so one request rebuilds, others wait
  • Refresh before expiry; add random jitter to TTLs
Penetration

Requests for keys that don't exist (e.g. id=-1) always miss and always hit the DB.

  • Fix: cache the "not found" result briefly
  • Bloom filter in front ({{ref:ch-toolbox}})
Avalanche

Many keys expire at the same moment, or the cache cluster restarts; the DB is flooded.

  • Fix: randomise TTLs
  • Replicated cache cluster, warm-up on start
Hot key

One celebrity key gets millions of reads and overloads a single cache node.

  • Fix: local in-process cache layer
  • Replicate the key as key#1…key#N

CDN: a cache spread across the planet

A Content Delivery Network is a set of servers ("edge locations") in hundreds of cities that keep copies of your static files. A user in Chennai downloads your logo from a Chennai edge server instead of your origin in Mumbai or Virginia.

Pull CDN

Edge fetches from your origin on the first request, then caches it. Easy; first user per region pays the miss. Most common (CloudFront, Cloudflare).

Push CDN

You upload content to the CDN in advance. More control, good for big files that rarely change (videos, game patches).

Bust stale files with versioned file names (app.3f9a2c.js) instead of waiting for TTLs or purging.

Common trap

"Just add a cache" without asking how stale is acceptable? A menu can be 10 minutes old. A bank balance or seat availability usually can't. Caching is a deliberate trade of freshness for speed; say the trade-off out loud.

Lock it in

Flasks on the counter: hit fast, miss once, throw out the stale.

Default answer: cache-aside + TTL + delete-on-write, Redis as the store, LRU eviction. Name the risks: stampede, penetration, avalanche, hot keys. "There are only two hard things in computer science: cache invalidation and naming things."

Interview questions

On a write, why delete the cache key instead of updating it?

Two concurrent writers can update the DB in one order and the cache in the opposite order, leaving the cache permanently wrong. Deleting is idempotent and order-safe: the next read reloads the true value from the DB. (A small race still exists with a concurrent reader; delayed double-delete or short TTLs cover it.)

What should and shouldn't be cached?

Cache data that is read far more than written, expensive to compute, and tolerant of slight staleness: product pages, profiles, feeds, configuration, session data. Be careful with data needing strict correctness (balances, inventory at checkout) or that is unique per request with no reuse.

Redis vs Memcached?

Both are in-memory key-value stores. Redis has rich data types (lists, sets, sorted sets, hashes, streams), persistence, replication, pub/sub and Lua scripts; it's the usual default. Memcached is simpler, multi-threaded and purely a cache of strings, good for very simple high-throughput caching.
