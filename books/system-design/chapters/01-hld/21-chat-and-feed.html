Case studies: a chat app and a news feed

Two classics that test real-time delivery and fan-out. Same building blocks as before, assembled differently.

A. Design a chat app (WhatsApp-style)

Requirements
  • 1:1 and group chats (up to 256)
  • Delivered and read receipts
  • Messages reach offline users when they return
  • Online/last-seen presence
  • History synced across devices
Key numbers
  • 500M DAU × 40 messages/day = 20B/day
  • ≈ 200K messages/s avg, ~600K peak
  • ~100 bytes each → ~2 TB/day of text
  • Hundreds of millions of open connections
  1. SendAsha's app sends the message (with a client-generated ID for dedup) over her WebSocket to chat server 7.
  2. Persist and ackThe message gets a time-sortable ID and is written to the message store; Asha sees one tick (sent).
  3. LocateThe router looks up Bikram in the session registry: he's on chat server 3.
  4. DeliverServer 3 pushes it down Bikram's socket; his app acks; Asha sees two ticks (delivered). If Bikram is offline, a push notification is sent and the message waits; when he reconnects, his app syncs everything after its last-seen message ID.
  5. Read receiptWhen Bikram opens the chat, a "read" event flows back the same way (blue ticks).

Groups: the router fans a message out to each member's server (small groups) via Kafka. Ordering is per chat, guaranteed by keying Kafka partitions and Cassandra partitions by chat_id. End-to-end encryption means servers store only ciphertext.

B. Design a news feed (Instagram/Twitter-style)

The core question: when Priya opens the app, how do we build her feed of posts from the 300 people she follows, in under 200 ms?

Push (fan-out on write)Pull (fan-out on read)Hybrid (what big apps do)
Write costHigh (one insert per follower)LowPush for normal users
Read costVery low (feed is precomputed)High (merge many timelines)Pull for celebrities, merge at read time
ProblemCelebrity posts, inactive followersSlow feed for users following manyMore complex, but balanced

Storage pattern: each user's feed is a Redis sorted set of post IDs scored by time (keep the latest ~800). The feed service reads IDs, then hydrates post details from a post cache, and ranks them (recency, affinity, engagement).

Lock it in

Chat: sockets + registry + per-chat order. Feed: push for most, pull for celebrities.

Real-time = WebSockets with a user → server registry. Feeds = hybrid fan-out with precomputed sorted sets in Redis.

Interview questions

How do you guarantee message ordering in a chat?

Order only matters within a conversation. Assign each message a monotonically increasing ID per chat (or a time-sortable Snowflake ID plus a per-chat sequence), route all messages of a chat through the same Kafka partition, and store them in a partition keyed by chat ID sorted by message ID. Clients render by that ID, not by arrival time.

How do you avoid fanning out to inactive users?

Only push into feeds of users active recently (say, the last 30 days). Inactive users get their feed built by pull when they return. This cuts write amplification dramatically.
