Beyond SOLID: DRY, KISS, YAGNI, composition and Demeter

A handful of short rules that every reviewer will quote at you. Know each one, its meaning, and when it's misused.

DRY
Don't Repeat Yourself

Every piece of knowledge (a rule, a formula) should live in one place. GST rate in five files = five bugs waiting. But don't merge code that only looks alike yet changes for different reasons.

KISS
Keep It Simple, Stupid

The simplest design that works is usually best. A for loop beats a clever 4-level stream pipeline nobody can read.

YAGNI
You Aren't Gonna Need It

Don't build features or abstractions for imagined futures. Build them when the need is real.

SoC
Separation of Concerns

Keep UI, business logic and data access in separate layers.

TDA
Tell, Don't Ask

Tell an object to do something instead of pulling its data out and deciding for it: wallet.withdraw(x), not if (wallet.getBalance() >= x) wallet.setBalance(…).

Fail fast
Fail fast

Validate early and throw clear errors at the boundary, instead of letting bad data travel deep into the system.

Composition over inheritance

At Ramu's chai stall

Ramu's nephew designed menu classes by inheritance: Chai, GingerChai, GingerElaichiChai, GingerElaichiSugarFreeChai, IcedGingerElaichiSugarFreeChai… Thirty classes later, every new flavour doubled the count. The fix: one Chai that has a list of add-ons. Build any combination at runtime.

Law of Demeter: talk only to your friends

A method should only call methods on: itself, its fields, its parameters, and objects it creates. Not on objects returned by those ("don't talk to strangers").

Interview questions

When does DRY go wrong?

When two pieces of code look the same by coincidence but represent different knowledge. Merging them into one shared function couples two features; when one changes, you add flags and ifs to the shared code until it's worse than the duplication. "Duplication is far cheaper than the wrong abstraction." (Sandi Metz)

Can SOLID principles conflict with KISS or YAGNI?

Yes. Over-applying SOLID creates interfaces with one implementation, factories for everything and deep indirection. Apply SOLID where change is expected or testing needs it; keep the rest simple. Principles are tools for managing change, not goals in themselves.
