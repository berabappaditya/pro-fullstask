Single Responsibility Principle

A class should have one, and only one, reason to change. One job, one owner.

At Ramu's chai stall

Ramu's first employee, Gopal, did everything: brewed tea, took cash, kept the accounts, cleaned up and handled deliveries. One April the GST rules changed. While Gopal was busy redoing the accounts, he forgot the milk on the stove and it boiled over. A change in tax rules broke tea making, two things that had nothing to do with each other except that one person did both.

Ramu hired a cook, a cashier and an accountant. Now a tax change only touches the accountant.

Definition

"A module should be responsible to one, and only one, actor." An actor is a group of people who would ask for changes: the finance team, the marketing team, the DBA. If two different groups can ask you to change the same class for different reasons, it has two responsibilities.

In plain words

A Swiss Army knife is handy, but if the scissors break you have to send the whole knife away, losing the blade too. Separate tools can be fixed, replaced and tested one at a time.

How to spot an SRP violation

The name has "And" or "Manager"

UserAndOrderManager, Utils, Helper.

Unrelated imports

java.sql, javax.mail and a PDF library in one file.

The "describe it" test

You can't say what it does without using "and".

Merge conflicts

Several teams keep editing the same file for different reasons.

Common trap

SRP does not mean "one method per class" or "tiny classes everywhere". A TaxCalculator with ten tax methods is fine: they all change for the same reason. Splitting too far scatters one idea across many files and lowers cohesion.

Lock it in

One cook, one stove. One class, one reason to change.

Ask: "Who would ask me to change this?" If the answer is more than one team, split it. In Spring, the Controller → Service → Repository layering is SRP at the architecture level.

Interview questions

How do you explain SRP to a junior developer?

Group together the things that change for the same reason, and separate the things that change for different reasons. If the tax team, the email team and the database team could each ask you to edit the same class, that class is doing three jobs and a change for one can break the others.

Does a Spring @RestController that validates input, calls a service and maps the response violate SRP?

Not necessarily. Its single responsibility is HTTP adaptation: turning requests into service calls and results into responses. Bean validation annotations and a mapper keep it thin. It violates SRP when business rules, SQL or transaction logic creep into the controller.
