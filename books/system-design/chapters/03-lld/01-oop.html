The four pillars of object-oriented programming

OOP organises code around objects that bundle data with the behaviour that acts on it. Four ideas make that work: encapsulation, abstraction, inheritance and polymorphism.

At Ramu's chai stall

Ramu orders automatic chai machines for every branch. A staff member presses "Make Masala Chai"; they never touch the boiler or the valve timings. The machine protects its insides (encapsulation) and offers simple buttons that hide the steps (abstraction). The new "Masala" model is built from the basic model plus a spice dispenser (inheritance). And every model has the same big "Brew" button, but each one brews its own way (polymorphism).

Class vs object

Class = the blueprint

The cookie cutter. Describes what data (fields) and behaviour (methods) every object of this kind has. class ChaiMachine.

Object = a real thing made from it

The actual cookies. Each has its own values. new ChaiMachine("Kolkata-01").

1. Encapsulation: protect your insides

Definition

Bundle data and the methods that operate on it in one unit, and restrict direct access to the data (private fields), exposing only controlled operations that keep it valid.

2. Abstraction: show what, hide how

Definition

Expose only the essential features of something through a simple interface, hiding implementation details. In Java: interfaces and abstract classes.

In plain words

You drive a car with a steering wheel and two pedals. You don't need to know about fuel injection. If the company swaps a petrol engine for an electric one, you still drive the same way. Encapsulation is about protecting the engine; abstraction is about simplifying how you use it.

3. Inheritance: an "is-a" relationship

Definition

A class (child/subclass) acquires the fields and methods of another (parent/superclass) using extends, and can add or override behaviour. Use it only for a true "is-a" relationship.

Common trap

Using inheritance just to reuse code ("Stack extends ArrayList" so I get add() for free). Now a Stack exposes add(index, x), which breaks stack rules. Deep hierarchies also become fragile: a change in a parent ripples to every child. Prefer composition ("has-a") unless it's truly "is-a" ({{ref:ch-beyond}}).

4. Polymorphism: one call, many behaviours

compile-time
Overloading

Same method name, different parameters, in one class. The compiler picks: price(Chai c), price(Chai c, Size s).

runtime
Overriding

A child redefines a parent's method. The JVM picks the version based on the actual object at runtime (dynamic dispatch).

"A PIE": Abstraction, Polymorphism, Inheritance, Encapsulation.

Encapsulation protects (private fields + validating methods). Abstraction simplifies (interfaces). Inheritance reuses for "is-a" only. Polymorphism replaces if (type == …) chains with overridden methods.

Interview questions

What's the difference between encapsulation and abstraction?

Encapsulation is about hiding data and protecting an object's internal state (implementation level: private fields, getters, validation). Abstraction is about hiding complexity and exposing only what's needed to use something (design level: interfaces, abstract methods). Encapsulation is how you achieve the information hiding that abstraction promises.

Can you override a static or private method?

No. Private methods aren't visible to subclasses, so a same-named method in a child is a new method. Static methods belong to the class; a same-signature static method in a child hides the parent's (method hiding), and which one runs depends on the reference type at compile time, not the object.
