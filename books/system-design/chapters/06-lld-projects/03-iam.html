LLD project: a multi-level IAM and authentication system

Identity and Access Management answers two questions on every request: who is this, and how sure are we (authentication), and what may they do on this exact resource (authorization), with permissions that flow down an organisation's hierarchy.

At Ramu's chai stall

Ramu Chai Pvt Ltd now has a finance department and an operations department, each with projects (payroll, the Kolkata branch). Ramu's rules: the owner can do anything anywhere. The finance team can view everything in finance and edit payroll. Contractors may edit operations files but may never delete anything there. And approving salary payouts needs not just a password but also the OTP on your phone; if you logged in with only a password, you're asked for the OTP right then.

"Permissions flow down the hierarchy", "a deny beats any allow", and "sensitive actions need a stronger login" are the three ideas behind AWS IAM, Google Cloud IAM and every serious enterprise access system.

Step 1 · Requirements

Authentication (multi-level)
  • Password login (level 1)
  • One-time password / TOTP (level 2)
  • Hardware security key (level 3)
  • Step-up: raise the level mid-session for sensitive actions
  • Sessions expire; lock out after repeated failures
Authorization (multi-level)
  • Resource hierarchy: organisation → department → project → resource
  • Roles bundle permissions (Viewer, Editor, Admin, PayrollApprover)
  • Bind roles to users or groups at any level; they inherit downward
  • Explicit deny policies override allows
  • Conditions (required auth level, time, network)
  • Default deny; every decision explainable and audited

Step 4 · How a decision is made

  1. CollectWalk from the resource up to the root, collecting every binding whose principal is this user or one of their groups.
  2. Deny firstIf any matching deny binding grants this permission and its condition holds → DENY. Nothing can override an explicit deny.
  3. Then allowIf an allow binding grants the permission and all its conditions hold → ALLOW.
  4. Step up?If an allow would match except that the session's authentication level is too low → STEP_UP_REQUIRED (ask for OTP or a security key, then retry).
  5. Default denyNothing matched → DENY. Access must always be granted on purpose.
  6. Explain and auditReturn the reason and the trace (which binding decided), and log the decision.

    Step 6 · Making it fast and safe in production

    Cache decisions

    Cache (user, permission, resource) → decision for a short TTL, and bump a policy version on every change so caches invalidate instantly. Authorization runs on every request, so it must be cheap. ({{ref:ch-cache}})

    Central engine, local enforcement

    Services call a shared policy engine (or embed a library fed with policies), and enforce at a single choke point: the API gateway or an aspect.

    Tokens carry identity, not permissions

    Put the user ID, groups and auth level in a short-lived signed token; look permissions up at check time so revoking a role takes effect quickly. ({{ref:ch-security}})

    Least privilege + audit

    Default deny, narrow roles, time-limited elevated access, and an immutable log of every decision with its reason.

    Lock it in

    Who and how sure → what, where, and walk up the tree. Deny wins. Silence means no.

    Authentication is a chain of factors that raises a session's level; authorization collects inherited bindings, applies explicit deny → conditional allow → step-up → default deny, and explains every decision.

    Interview questions

    RBAC vs ABAC?

    Role-Based Access Control grants permissions through roles assigned to users or groups; simple to reason about and audit. Attribute-Based Access Control evaluates attributes of the user, resource, action and environment (department, owner, time, IP, MFA) against rules; more expressive but harder to audit. Most real systems use RBAC with conditions, i.e. a hybrid.

    What is step-up authentication?

    Asking an already logged-in user for a stronger factor only when they attempt a sensitive action (approve a payout, change bank details). The session's assurance level rises for a limited time. It balances security with convenience: no OTP for reading a menu, OTP for moving money.

    Why must deny override allow?

    Allows come from many places (inherited org roles, groups, project roles), so it's easy to grant something accidentally. A deny is a guardrail that must hold no matter which allow exists, e.g. "contractors may never delete in operations". If allows could override it, any new broad role would silently break the guardrail.
