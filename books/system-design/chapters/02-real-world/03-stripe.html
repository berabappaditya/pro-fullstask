How Stripe handles huge payment traffic

Stripe's problem isn't only volume; it's that every request moves real money. Its design is built around never charging twice, never losing a payment, and shedding the right traffic when overloaded.

At Ramu's chai stall

A hotel manager phones Ramu: "Send 500 cups for the conference, charge our account." The line crackles and drops. Did Ramu hear the order? The manager calls again: "Send 500 cups…". If Ramu simply obeys, the hotel gets 1,000 cups and a double bill. So Ramu asks every caller for an order reference: "Is this order H-77? Already noted, here's the same confirmation." Now calling twice is safe.

That reference is Stripe's idempotency key, the most important idea in payment API design.

The request path

Idempotency keys: retries without double charges

Networks fail after the server has done the work but before the client hears back. The client can't tell "never arrived" from "done, reply lost". So the client sends a unique Idempotency-Key header (a UUID it generates once per purchase) and reuses it on every retry. Stripe stores the first result for that key and replays it for any repeat.

A payment is a state machine

Surviving Black Friday: rate limiters and load shedders

Stripe has described running four layers of protection. The first two limit individual users; the last two protect the whole fleet by dropping less important traffic first.

This is load shedding with priorities: when there isn't enough capacity for everything, decide in advance what to drop. A merchant's dashboard chart can wait; a customer's checkout can't. ({{ref:ch-rate}}, {{ref:ch-reliability}})

Data: thousands of shards, moved without downtime

Stripe's main online database platform, DocDB, is built on MongoDB Community. Applications talk to a fleet of Go database proxies, which look up a chunk metadata service to route each query to the right shard (a replica set with automatic failover). Every change also streams to Kafka and on to object storage.

Shards fill up unevenly, so data must move between them while payments keep flowing. Stripe's Data Movement Platform does it in six steps, the same pattern you'd use for any live resharding ({{ref:ch-sharding}}):

  1. RegisterRecord the planned move in the metadata service; build indexes on the target shard.
  2. Bulk importCopy a point-in-time snapshot of the chunk to the target.
  3. ReplicateReplay every write made since the snapshot from the change stream, until the target catches up.
  4. VerifyCompare source and target snapshots for completeness and correctness.
  5. Switch trafficBriefly block writes to that chunk on the source, let replication drain, update the route. The cutover takes under two seconds; requests that fail during it succeed on retry.
  6. Clean upMark the move complete and delete the chunk from the source.

Three more habits worth copying

Webhooks done right

Events are signed (an HMAC header the merchant verifies), retried with exponential backoff for days, and delivered at-least-once and possibly out of order. Merchants must make handlers idempotent by event ID. ({{ref:ch-queue}})

Dated API versions

Each account is pinned to the API version it started with (versions are dates). Stripe translates responses for old versions, so a 2017 integration keeps working while new accounts get new behaviour. ({{ref:ch-api}})

Double-entry ledger

Every movement of money is recorded as balanced debits and credits. If the books don't sum to zero, something is wrong, and it's detectable. (Built in the banking project, {{ref:ch-banking}}.)

Interview questions

How would you implement idempotency keys?

Store (merchant ID, key) with a unique constraint, plus a hash of the request body, a state (started/completed) and the saved response. The first request inserts the row and does the work; duplicates either get the saved response, a 409 if the first is still running, or a 422 if the body differs. Make the side effects themselves idempotent too (pass the key to downstream systems), and expire keys after a retention window such as 24 hours.

Design a payment gateway that never double-charges.

Idempotency keys at the API, unique constraints in the database, a state machine per payment with each transition persisted before the next external call, idempotency references passed to card networks, a reconciliation job comparing your records with bank settlement files, and an append-only double-entry ledger. Prefer "unknown/pending" plus reconciliation over guessing.

What is load shedding and how is it different from rate limiting?

Rate limiting caps what each client may send, whatever the system's state. Load shedding looks at the system's own health (CPU, in-flight requests, queue length) and drops some requests when it's near overload, choosing the least important ones first. Both return errors early instead of letting the whole service slow to a halt.
