HashMap internals: the most asked Java question

An array of buckets; the key's hash picks the bucket; equals finds the key inside it. Too many keys? Double the array. Too many in one bucket? Turn it into a tree.

In Ramu's kitchen

Ramu's spice rack has 16 numbered slots. To store a jar, he works out a number from its label and puts it in that slot. If two labels land in the same slot, he hangs the second jar under the first (a chain). When the rack is 75% full, he buys a rack twice as big and re-sorts everything. If one slot ever has a long dangle of 8 jars, he arranges that slot alphabetically so finding a jar takes fewer looks (a tree).

Step by step: put(key, value)

  1. HashCall key.hashCode() (null key → hash 0, bucket 0) and spread it: h ^ (h >>> 16) so the high bits influence the bucket too.
  2. Index(n - 1) & hash. Capacity is always a power of two, so this bit-mask is a fast modulo.
  3. Empty bucket?Place a new node there. Done.
  4. Occupied?Walk the chain. If a node has the same hash and equals the key, replace its value (and return the old one). Otherwise append a new node at the tail.
  5. TreeifyIf the chain reaches 8 nodes (and the table has ≥ 64 slots), convert that bucket to a red-black tree. If the table is smaller, resize instead. Trees shrink back to lists at 6.
  6. ResizeIf size exceeds capacity × loadFactor, double the table. Each node either stays at index i or moves to i + oldCapacity, depending on one bit of its hash, so no rehashing is needed.

Why it matters: a bad hashCode destroys performance

Interview tip

If you know roughly how many entries you'll store, size the map upfront: HashMap.newHashMap(10_000) (Java 19+) creates a map that holds 10,000 entries without resizing. The older new HashMap<>(10_000) sets capacity, which resizes at 75% of the rounded-up size.

Common trap

Using HashMap from several threads. Concurrent puts can lose entries, and in Java 7 a concurrent resize could even create a cycle and hang get() forever. Use ConcurrentHashMap ({{n:ch-juc}}).

Interview questions

Why is HashMap capacity always a power of two?

So the bucket index can be computed with a bitwise AND (hash & (n-1)), which is much faster than modulo, and so resize can split each bucket into "stay" and "move by oldCap" using a single bit. The constructor rounds any requested capacity up to the next power of two.

Why treeify at 8 and untreeify at 6?

With a decent hash function, the chance of 8 entries in one bucket is about 1 in 10 million (Poisson distribution), so trees appear only with bad hashes or attacks. The gap between 8 and 6 avoids flipping back and forth when the count hovers around the threshold.

What happens with a null key?

HashMap allows one null key, stored in bucket 0 with hash 0. ConcurrentHashMap and TreeMap (natural ordering) don't allow null keys.

How does get() work?

Compute the same spread hash, go to index hash & (n-1), check the first node (hash equal and key == or equals), then walk the list or search the tree. Return the value or null.
