The Collections map and Big-O cheat sheet

Ask three questions: do I need order, do I need uniqueness, do I look things up by key? The answers pick the collection.

In Ramu's kitchen

The ticket rail where orders are clipped in arrival order is a List (order, duplicates OK). The guest list of loyalty members is a Set (each person once). The spice rack where you find a jar by its label is a Map (key → value). The "next order to cook" queue, with VIPs jumping ahead, is a PriorityQueue.

Choosing in 10 seconds

default list
ArrayList

Contiguous array: cache-friendly and fast. LinkedList almost never wins in practice.

stack / queue
ArrayDeque

Faster than Stack (legacy, synchronized) and LinkedList. push/pop, offer/poll.

lookup by key
HashMap

Need sorted keys or range queries (floorKey, headMap)? TreeMap.

top-K / scheduling
PriorityQueue

Min-heap by default; pass Comparator.reverseOrder() for max-heap.

LRU cache
LinkedHashMap

Access-order mode plus removeEldestEntry. See {{n:ch-lists-trees}}.

many threads
ConcurrentHashMap

Never a plain HashMap shared across threads.

Lock it in

Rail, guest list, spice rack, VIP queue.

List = ordered with duplicates, Set = unique, Map = key → value, Queue = process in order. Default to ArrayList, HashMap, ArrayDeque.

Interview questions

ArrayList vs LinkedList: which is faster to insert in the middle?

On paper LinkedList is O(1) once you're at the node, but finding the position is O(n) and its nodes are scattered in memory. ArrayList shifts elements with a fast System.arraycopy, so in practice it's usually faster even for middle inserts unless the list is huge and you already hold an iterator.

Difference between HashMap and Hashtable?

Hashtable is legacy: every method synchronized (slow), no null keys or values. HashMap is unsynchronized and allows one null key. For thread safety use ConcurrentHashMap, not Hashtable.
