Strings and the string pool

A String can never change after it's created. That immutability makes strings safe to share, cache and use as map keys, and it's why you build long text with StringBuilder.

In Ramu's kitchen

The menu card on the wall is laminated. Nobody can scribble on it, so every waiter can point customers to the same card safely. If Ramu wants "Masala Chai" to read "Masala Chai (Large)", he prints a new card. Popular cards are kept in one card box (the string pool) so the kitchen never prints a duplicate of "Masala Chai".

Why immutable?

Safe sharing

The pool can hand the same object to everyone because nobody can change it.

Thread-safe for free

No locks needed to read a string from many threads.

Reliable map keys

The hash code is computed once and cached; a key can't change after you put it in a HashMap.

Security

A file path or DB URL you validated can't be swapped underneath you.

Interview questions

How many objects does new String("chai") create?

Up to two: the literal "chai" in the string pool (if it isn't already there, created when the class is loaded) and one new String object on the heap from new. Calling .intern() returns the pooled one.

Why is String a popular HashMap key?

It's immutable (the key can't change after insertion), its hashCode is cached after the first call, and equals/hashCode are correctly implemented.

Why are passwords often kept in char[] rather than String?

A String can't be wiped and may linger in memory (and the pool) until GC, appearing in heap dumps. A char array can be overwritten with zeros right after use.
