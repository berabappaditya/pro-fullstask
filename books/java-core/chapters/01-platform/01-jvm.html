How Java runs: JDK, JRE and the JVM

javac turns your code into bytecode; the JVM loads that bytecode and runs it, first by interpreting it, then by compiling the hot parts to native machine code.

In Ramu's kitchen

Ramu writes his recipes in Bengali. His new branches are in Chennai, Pune and Delhi, where cooks speak different languages. Instead of writing the recipe four times, he translates it once into a universal kitchen picture-language that every head cook in every city has been trained to read. Each head cook then reads the pictures and tells their own team what to do. Recipes the cook makes 500 times a day, he memorises completely so he no longer needs to look at the card.

Bengali recipe = .java source. Picture-language = bytecode. The trained head cook in each city = the JVM for each operating system. Memorising the popular recipes = the JIT compiler.

JDK, JRE, JVM: three boxes, one inside the other

From source to running program

  1. Compilejavac Order.java checks types and produces Order.class, containing platform-independent bytecode.
  2. LoadWhen the class is first needed, a class loader finds the .class file (bootstrap → platform → application loaders, parent first) and loads it into memory.
  3. LinkThe verifier checks the bytecode is safe; static fields get default values; symbolic references are resolved.
  4. InitialiseStatic initialisers run, once per class.
  5. ExecuteThe interpreter runs bytecode immediately. Methods called often become "hot" and the JIT (C1, then C2) compiles them to optimised native code.
  6. ManageWhile running, the garbage collector reclaims objects no one references.

Why the JIT matters

Interpreter

Starts instantly, runs every bytecode one by one. Slow for loops that run millions of times.

JIT (C1 → C2)

Profiles the running code and compiles hot methods to native code with optimisations: inlining, loop unrolling, escape analysis, removing unused locks.

Warm-up

A Java service is slower for its first seconds; that's why load tests "warm up" first. Java 25 adds ahead-of-time profiling to shorten this.

GraalVM native image

Compiles the whole app ahead of time into a native binary: very fast startup, lower memory, no JIT. Popular for serverless.

Common trap

"Java is interpreted, so it's slow." Modern JVMs compile hot code to native machine code, often as fast as C++ for long-running servers. What Java pays is startup time and memory, not steady-state speed.

Lock it in

Write, Compile, Load, Link, Init, Run, JIT.

JDK ⊃ JRE ⊃ JVM. Bytecode is the portable middle layer; the JVM per OS is what makes "write once, run anywhere" true. Hot code gets JIT-compiled to native.

Interview questions

Is Java compiled or interpreted?

Both. javac compiles source to bytecode ahead of time. At runtime the JVM interprets bytecode, and the JIT compiles frequently executed methods to native code. So it's a hybrid.

What is a class loader and what is parent delegation?

A class loader finds and loads .class files. Java has bootstrap (core classes), platform, and application (your classpath) loaders. Before loading a class, a loader first asks its parent; only if the parent can't find it does it load it itself. This stops your code from replacing core classes like java.lang.String.

Why is the main method public static void main(String[] args)?

public so the JVM can call it from outside the class, static so it can be called without creating an object, void because the exit code is returned via System.exit, and String[] for command-line arguments. (Java 25 also allows simpler instance main() methods in compact source files, mainly for learning and scripts.)
