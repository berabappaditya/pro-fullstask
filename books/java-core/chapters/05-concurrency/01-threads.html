Processes, threads and the thread lifecycle

A process is a running program with its own memory; a thread is one path of execution inside it. Threads share the heap, which makes them fast to coordinate and easy to break.

In Ramu's kitchen

A process is the entire restaurant: building, stove, fridge, ingredients. When you run a Java program, the operating system opens one restaurant for it with its own private memory. A thread is one chef working inside. Every restaurant opens with at least one chef (the main thread). Multithreading is hiring more chefs so several dishes cook at the same time, all sharing the same kitchen. Two chefs grabbing the same pan is where the trouble starts.

Concurrency vs parallelism

Concurrency: several tasks in progress at once, maybe taking turns on one core (one chef juggling three pots). Parallelism: tasks literally running at the same instant on different cores (three chefs, three stoves). Threads give you concurrency; multiple cores turn it into parallelism.

The thread lifecycle

join()

"Pause my thread until that thread finishes." The head chef won't send the dish out until the sauce chef is done.

sleep(ms)

Pause the current thread. Keeps any locks it holds.

wait() / notify()

Called inside synchronized on the same object. wait() releases the lock and sleeps until notified. Low-level: prefer java.util.concurrent tools.

interrupt()

A polite "please stop" flag. Blocking calls throw InterruptedException; your code should finish up and exit.

Daemon threads

Background helpers (setDaemon(true)) that don't keep the JVM alive; e.g. GC threads.

Priority

setPriority(1..10) is only a hint to the OS. Never rely on it for correctness.

Lock it in

Hired, clocked in, waiting for the oven, gone home.

NEW → RUNNABLE → (BLOCKED / WAITING / TIMED_WAITING) → TERMINATED. sleep keeps locks, wait releases them.

Interview questions

Difference between sleep() and wait()?

sleep is a static Thread method, can be called anywhere, keeps held locks, and resumes after the time. wait is an Object method, must be called while holding that object's monitor (inside synchronized), releases the monitor, and resumes on notify/notifyAll, timeout or interrupt. Always call wait in a loop that re-checks the condition (spurious wakeups).

How do you stop a thread?

Cooperatively: call interrupt() (or set a volatile flag) and have the thread check Thread.currentThread().isInterrupted() and handle InterruptedException by cleaning up and returning. Thread.stop() was deprecated and removed because it could leave objects half-updated.
