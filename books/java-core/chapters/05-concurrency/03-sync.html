Race conditions, synchronized, volatile and atomics

When threads read and write shared data without coordination, updates get lost. Locks give one-at-a-time access; volatile gives visibility; atomics give lock-free single-variable updates.

In Ramu's kitchen

Two chefs read the order board: "3 pizzas left to make". Both grab ingredients, both make a pizza, and both walk back and write "2 pizzas left", because both did the maths from the old number they saw. Two pizzas were made but the board only dropped by one. That's a race condition.

The fix: the board now has a marker with a key attached. You may only update the board while holding the marker, and only one chef can hold it. Updates can no longer overlap.

Synchronized method vs synchronized block

Rule of thumb

Lock the smallest section that touches shared data, and always use the same lock object for the same data. Locks only work if everyone agrees to use the same marker. Java monitors are reentrant: a thread holding a lock can enter another synchronized method on the same object without deadlocking itself.

Interview questions

What is a race condition?

When the correctness of a result depends on the timing of threads accessing shared mutable data, e.g. two threads doing check-then-act (if (!map.containsKey(k)) map.put(k, v)) or read-modify-write (count++) without synchronization.

Does volatile make count++ thread-safe?

No. volatile guarantees each read sees the latest write, but count++ is still three separate operations, so two threads can read the same value and both write value+1. Use AtomicInteger or a lock.

What is CAS?

Compare-and-swap: a single CPU instruction that sets a memory location to a new value only if it still holds the expected old value, returning whether it succeeded. Atomic classes loop on CAS until it succeeds. It avoids blocking but can suffer the ABA problem (solved with AtomicStampedReference).

Why is double-checked locking broken without volatile?

The write of the singleton reference can be reordered before the constructor finishes, so another thread could see a non-null but half-built object. Declaring the field volatile forbids that reordering. (Simpler: use an enum or a holder class.)
