Creating threads: Thread, Runnable and Callable

The work always lives in a run() method; only start() creates a new thread. Prefer Runnable (or Callable) tasks handed to a pool.

In Ramu's kitchen

Extending Thread is like welding a recipe to one specific chef: that chef can only ever make that dish and can't take on any other identity. Implementing Runnable is writing the recipe on a card: any chef can pick it up, and later a whole team of reusable chefs (a thread pool) can share a stack of cards.

Classic trap: start() vs run()

Calling chef.run() creates no new thread: the main thread just runs the method like any normal call. Only start() asks the JVM to spin up a new thread. Calling the chef's phone (run()) isn't the same as the chef showing up to work (start()). And calling start() twice throws IllegalThreadStateException.

Why Runnable wins

Inheritance stays free

Your class can still extend something else.

Separation of concerns

The task (what to do) is separate from the worker (how it runs): easier to test.

Pools expect it

Executors accept Runnable and Callable tasks, not Thread subclasses.

Lambda-friendly

A task can be one clean line.

Interview questions

What happens if you call run() instead of start()?

The method runs synchronously on the calling thread; no new thread is created, so there is no concurrency. Printing Thread.currentThread().getName() inside would show "main".

What happens to an uncaught exception in a thread?

That thread terminates and the exception goes to its UncaughtExceptionHandler (by default, printed to stderr). Other threads keep running. In an ExecutorService with submit(), the exception is captured in the Future and only seen when you call get(), which is a common source of "silent" failures.
