Deadlock, livelock and starvation

A deadlock is two or more threads each waiting for a lock the other holds, forever. No crash, no error, just a frozen program.

In Ramu's kitchen

A dish needs both the frying pan and the spatula. Chef A grabs the pan. At the same moment Chef B grabs the spatula. Chef A waits for the spatula ("I won't let go of my pan!"); Chef B waits for the pan ("I won't let go of my spatula!"). Both follow the rules, both wait forever. The kitchen is frozen.

LivePan and spatula: run both chefs, then fix it with lock ordering

The four ingredients (Coffman conditions)

1
Mutual exclusion

Only one holder per lock.

2
Hold and wait

Holding one lock while asking for another.

3
No preemption

Locks can't be forcibly taken away.

4
Circular wait

A waits for B, B waits for A. Break this one with a global lock order.

Livelock

Two chefs keep politely stepping aside for each other in a corridor: both active, neither progressing. Fix with random back-off.

Starvation

One chef never gets the stove because others always grab it first. Fix with fair locks (new ReentrantLock(true)) or bounded queues.

Lock it in

Pan before spatula, always.

Deadlock needs all four conditions; break circular wait with lock ordering, or use tryLock with timeouts. Diagnose with a thread dump.

Interview questions

How would you prevent deadlock in a bank transfer between two accounts?

Always lock the two accounts in a consistent global order, e.g. by account id: lock the smaller id first, then the larger, regardless of transfer direction. Alternatively use tryLock with timeout and retry, or avoid application locks entirely with a single database transaction using SELECT … FOR UPDATE in id order.

Can a deadlock happen with a single lock?

Not with Java's reentrant monitors on the same thread. But a thread can block forever waiting on itself in other ways, e.g. a task submitted to a single-thread executor that waits for another task submitted to the same executor (thread-starvation deadlock).
