ThreadLocal

A ThreadLocal gives each thread its own copy of a variable (each chef's own apron pocket). Spring uses it for the current transaction, security context and request attributes.

Common trap

In a thread pool the thread is reused, so a value left in a ThreadLocal leaks into the next request on that thread (wrong user!) and can leak memory. Always remove() in a finally. In Java 25 prefer ScopedValue, which is immutable and automatically ends with its scope.

Virtual threads (Java 21)

Great for

I/O-bound request handling: REST calls, DB queries, message consumers. Write simple blocking code, get reactive-like scalability.

Don't

Pool them (they're cheap; create one per task). Use them for CPU-heavy work (no speed-up). Forget the DB pool is still the limit: use a Semaphore or pool size.

Pinning

In Java 21–23 a virtual thread blocking inside synchronized pinned its carrier. Java 24 (JEP 491) fixed this for synchronized; native calls can still pin.

Structured concurrency (preview)

StructuredTaskScope treats subtasks as one unit: if one fails, the others are cancelled. Still a preview in Java 25.

Lock it in

Rail, countdown, tokens, read-many-write-one.

Use merge/compute on ConcurrentHashMap, bounded BlockingQueues for producer–consumer, and virtual threads for blocking I/O, not for CPU work.

Interview questions

How does ConcurrentHashMap achieve thread safety?

Java 7 used 16 segments each with its own lock. Java 8+ uses a Node array like HashMap: inserting into an empty bin uses CAS; otherwise it synchronizes on the bin's head node, so only one bucket is locked. Reads are lock-free using volatile reads. Size is tracked with LongAdder-style counter cells.

synchronized vs ReentrantLock?

Both are reentrant mutual-exclusion locks with the same memory semantics. ReentrantLock adds tryLock (with timeout), lockInterruptibly, optional fairness, and multiple Condition objects, but you must unlock in finally. synchronized is simpler and released automatically.

CountDownLatch vs CyclicBarrier?

CountDownLatch: one or more threads wait until a count reaches zero; other threads count down; it can't be reset. CyclicBarrier: a fixed number of threads wait for each other at a barrier point, then all proceed; it resets for reuse and can run a barrier action.

When would virtual threads not help?

CPU-bound work (cores are the limit), code limited by a small downstream resource (connection pools), and code relying heavily on ThreadLocal caches of expensive objects (one per virtual thread means millions).
