Spring Boot in practice: insert 10,000 records with multithreading

Split the list into chunks, save each chunk on a pool thread in its own transaction, and wait for all of them. A very popular SDE-2 interview question.

In Ramu's kitchen

10,000 plates need to go from the kitchen to the storeroom. One waiter carrying one plate at a time takes all night. The smart way: stack the plates into trays of 500 (chunks) and let a team of 5 waiters (a thread pool) carry trays at the same time. Same plates, a fraction of the time. But the storeroom has only so many doors (database connections), so hiring 50 waiters wouldn't help.

The plan maps onto Spring's tools: chunking (split the list), ThreadPoolTaskExecutor (Spring's wrapper around the Executor framework), @Async ("run this method on a pool thread"), and CompletableFuture (the receipt that tells us when every chunk is done).

The #1 @Async trap

@Async (like @Transactional) works through a Spring proxy. If a method calls an @Async method in the same class (self-invocation), the proxy is bypassed and it silently runs on the same thread: no parallelism. That's exactly why the worker is a separate bean from the orchestrator below. Also: @Async methods must be public and return void, Future or CompletableFuture.

Interview tip: say the trade-offs

Each chunk commits separately, so a failure in chunk 7 leaves chunks 1–6 saved: the job is not atomic. Mention how you'd handle it: idempotent upserts, a job-status table, retrying failed chunks, or Spring Batch (chunk-oriented processing with restart). For very large loads (millions of rows) or recurring jobs, Spring Batch or the database's bulk loader is the better answer. And the thread count is capped by the connection pool, not the CPU.

Interview questions

Why not just use one @Transactional around all 10,000 inserts on many threads?

A Spring transaction is bound to one thread (via ThreadLocal) and one connection. Work on other threads doesn't join it. So either it's one thread with one big transaction (atomic, slower, huge persistence context: flush/clear every N rows), or several threads with one transaction each (faster, not atomic).

Why does GenerationType.IDENTITY break batching?

With IDENTITY the database generates the id on insert, and Hibernate needs that id immediately to manage the entity, so it must execute each INSERT right away instead of batching them. SEQUENCE lets Hibernate get ids ahead of time (allocationSize) and batch the inserts.

What happens if an exception is thrown in an @Async method?

With a CompletableFuture return type, the future completes exceptionally and join() rethrows it as CompletionException; that chunk's transaction rolls back. With void return, it goes to the AsyncUncaughtExceptionHandler (default: logged), easy to miss.
