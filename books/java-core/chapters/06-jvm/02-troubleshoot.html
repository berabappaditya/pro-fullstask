Troubleshooting a production JVM

High CPU? Take thread dumps. Memory climbing? Take a heap dump. Slow and spiky? Read the GC log. Then fix the code, not the flags.

The incident playbook (say this in interviews)

  1. StabiliseScale out or roll back first. Protect users before debugging.
  2. Look at metricsCPU, heap after GC, GC pause time, thread count, pool usage, p99 latency, error rate (Actuator + Micrometer + Grafana).
  3. Capture evidence3 thread dumps 5–10 s apart; a heap dump if memory is the issue; a 60 s JFR recording.
  4. Find the culpritSame stack in every dump = stuck or hot code. Dominator tree = what holds memory.
  5. Fix and preventFix the code; add a timeout, bound, or test; add an alert so you see it earlier next time.

Interview questions

Your Spring Boot service's memory keeps growing until it's OOM-killed. How do you investigate?

Check whether it's heap or native: if heap-after-GC keeps rising, it's a heap leak; take two heap dumps some time apart and compare the dominator trees in MAT (common: unbounded caches, static maps, ThreadLocals, huge sessions). If heap is flat but RSS grows, use Native Memory Tracking (threads, direct buffers, metaspace). Make sure MaxRAMPercentage leaves room for non-heap memory in the container.

What's in a thread dump?

For every thread: name, state (RUNNABLE, BLOCKED, WAITING…), the native id, the full stack trace, and the locks it holds or is waiting for. The JVM also reports detected deadlocks at the end.
