Generics, wildcards and type erasure

Generics let the compiler check what goes into a container, so you get type errors at compile time instead of ClassCastException at runtime.

In Ramu's kitchen

A jar labelled "Spices only" (Jar<Spice>) stops anyone from putting sugar in it. A helper who only takes things out to taste can accept any jar of any kind of spice (? extends Spice). A helper who only puts chilli in can use a jar of chilli, of spices, or of anything at all (? super Chilli).

PECS: Producer Extends, Consumer Super

Type erasure

Generics exist only at compile time. The compiler checks types, inserts casts, and then erases T to its bound (usually Object). At runtime List<String> and List<Integer> are the same class. Consequences:

No new T()

T is unknown at runtime. Pass a Supplier<T> or Class<T> instead.

No instanceof List<String>

Only instanceof List<?> works.

No overloads that differ only by type argument

f(List<String>) and f(List<Integer>) erase to the same signature.

No primitives

List<int> isn't allowed; boxing is needed.

Lock it in

PECS: Producer Extends, Consumer Super.

Generics = compile-time safety, erased at runtime. Read from ? extends, write to ? super.

Interview questions

Is List<Integer> a subtype of List<Number>?

No. Generics are invariant. If it were, you could add a Double to a list of Integers through the Number reference. Use List<? extends Number> to accept both. (Arrays are covariant, which is why Object[] a = new String[1]; a[0] = 1; throws ArrayStoreException.)

What is type erasure and why did Java choose it?

The compiler removes generic type information after checking it, replacing type parameters with their bounds and adding casts. It was chosen for backward compatibility: generic code from Java 5 runs alongside and on the same JVM as pre-generics code.
