Exceptions done right

Checked exceptions are problems the caller should plan for; unchecked exceptions are bugs or unrecoverable conditions. Errors are the JVM itself in trouble.

In Ramu's kitchen

"The milk supplier might not come" is a known risk; the recipe must say what to do (checked exception: the compiler forces you to handle or declare it). "The chef put salt instead of sugar" is a mistake; you fix the chef, not write a plan for it (unchecked). "The building is on fire" is not your recipe's problem (Error).

Do

Catch the most specific type. Keep the cause (new X(msg, e)). Use try-with-resources. Throw early (validate inputs), catch late (at a boundary that can act).

Don't

Catch Throwable/Exception and ignore it. Use exceptions for normal control flow. Return from finally (it hides the exception). Log and rethrow at every layer (duplicate logs).

Common trap

Spring's @Transactional rolls back only on unchecked exceptions by default. A checked exception will commit the transaction unless you add rollbackFor = Exception.class. See {{xref:spring-boot/ch-transactions}}.

Lock it in

Plan for checked, fix unchecked, flee from Error.

try-with-resources for anything closable. Wrap with cause, never swallow. finally always runs (except System.exit or a JVM crash).

Interview questions

What's the difference between throw and throws?

throw is a statement that throws an exception object right now. throws in a method signature declares which checked exceptions the method may pass up to its caller.

What happens if both try and finally return a value?

The finally value wins and any exception from try is discarded. That's why returning from finally is considered a bug.

What are suppressed exceptions?

In try-with-resources, if the body throws and then close() also throws, the close exception is attached to the main one as "suppressed" (e.getSuppressed()) instead of replacing it.
