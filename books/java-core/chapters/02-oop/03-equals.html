equals, hashCode, compareTo and immutability

If two objects are equal, they must have the same hashCode. Break that rule and HashMap and HashSet silently lose your data.

In Ramu's kitchen

Spice jars are stored on racks by the first letter of the label (the hash code), and inside a rack Ramu reads labels to find the exact jar (equals). If two jars both say "Haldi" but somebody files one under "H" and the other under "T", Ramu will look under "H", never find the second jar, and buy a duplicate. That's what happens when equal objects return different hash codes.

The contract

equals must be reflexive (a = a), symmetric (a = b ⇔ b = a), transitive, consistent, and x.equals(null) is false. hashCode: equal objects ⇒ equal hash codes. (Unequal objects may share a hash code; that's a collision, which is allowed.)

Common trap

Mutating a field used in hashCode while the object is inside a HashSet or used as a HashMap key. Its bucket no longer matches its hash, so contains and remove fail and the entry leaks. Keys should be immutable.

Comparable vs Comparator

How to make a class immutable

  1. Make the class finalso no subclass can add mutable state.
  2. All fields private finalassigned once in the constructor.
  3. No setters; "withX" methods return a new object instead.
  4. Defensive copiesof mutable inputs and outputs: this.items = List.copyOf(items).
  5. Or use a record, then still copy mutable components like lists in the compact constructor.
Lock it in

Same label, same rack.

Override equals and hashCode together, from the same fields. Map keys should be immutable. Comparable = one natural order; Comparator = any number of orders.

Interview questions

What is the difference between == and equals()?

== compares primitive values or, for objects, whether two references point to the same object. equals() compares logical equality as defined by the class; Object's default is the same as ==.

Can two unequal objects have the same hashCode?

Yes, that's a collision and it's legal; the map then uses equals within the bucket. Many collisions make lookups slower (O(log n) after treeification), so a good hash spreads values evenly.

Why are immutable objects good for concurrency?

Their state can't change after construction, so they can be shared between threads with no locks and no visibility problems (final fields are safely published by the Java memory model).
