Interfaces, abstract classes, records, enums and sealed types

An interface says what something can do; an abstract class shares how it's done. Records, enums and sealed types are modern shortcuts for data, fixed sets and closed hierarchies.

In Ramu's kitchen

"Anyone who can Deliver" is a job description: Swiggy, Zomato, or Ramu's nephew on a cycle can all do it, however different they are (interface). "Beverage" is a half-written recipe: every beverage is poured into a cup the same way, but how it's brewed is left to Chai, Coffee, Lassi (abstract class). The menu's sizes are only Small, Medium and Large, nothing else (enum). An order slip is just data (record).

Interview tip

When asked "interface or abstract class?", say: prefer interfaces for the contract (it keeps classes free to extend something else and makes mocking and DI easy), and add an abstract base class only to share real code between closely related implementations. Mention that Spring injects by interface type.

Common trap

The diamond problem with default methods: if a class implements two interfaces with the same default method, it must override it and can pick one with A.super.method(). Java never silently guesses.

Lock it in

Interface = can-do. Abstract = is-a, half-built. Record = data. Enum = fixed list. Sealed = closed family.

Sealed types + records + pattern-matching switch = exhaustive, compiler-checked handling of every case.

Interview questions

Why were default methods added in Java 8?

To evolve interfaces without breaking existing implementations. Collection needed stream() and forEach(); adding abstract methods would have broken every collection class ever written, so they were added as defaults.

Can a record have extra methods or fields?

It can have extra methods, static fields and static methods, and a compact or custom constructor. It can't declare extra instance fields, can't extend another class (it implicitly extends java.lang.Record), and its fields are final. It can implement interfaces.

Why is an enum a good way to write a Singleton?

The JVM guarantees exactly one instance per constant, it's thread-safe by class initialisation, and it's safe against reflection and serialization attacks that can break other singleton styles.
