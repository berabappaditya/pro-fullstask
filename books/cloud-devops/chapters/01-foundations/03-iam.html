IAM: who can do what to which resource

Every API call in the cloud is checked: which identity, which action, which resource, under which conditions. Grant the least privilege, prefer short-lived role credentials over long-lived keys.

In the food court

Staff don't get master keys. The baker's badge opens the oven room only, during his shift. A delivery partner gets a temporary pass valid for one hour. And the kitchen robot also has a badge (a role), so nobody tapes a key to it.

Do

Least privilege, scoped to resources. Roles/service accounts for workloads. SSO + MFA for humans. Separate accounts/projects per environment. Audit with CloudTrail / Cloud Audit Logs.

Don't

Use the root account. Put access keys in code, images or Git. Grant *:* or project Owner to apps. Share one role across unrelated services.

Lock it in

Badges, not master keys. Temporary passes, not copied keys.

Principal + action + resource + condition. Explicit deny wins, default deny. Workloads use roles/service accounts with short-lived credentials.

Interview questions

How does an app on EC2/EKS get AWS permissions without access keys?

EC2: an instance profile attaches a role; the SDK fetches temporary credentials from the instance metadata service (IMDSv2) and refreshes them. EKS: Pod Identity or IRSA maps a Kubernetes service account to an IAM role, giving each pod its own temporary credentials. No keys stored anywhere.

Identity-based vs resource-based policies?

Identity-based policies attach to a user/role and say what it can do. Resource-based policies attach to a resource (S3 bucket policy, SQS queue policy, KMS key policy) and say who can access it, including other accounts. Cross-account access usually needs both sides to allow.
