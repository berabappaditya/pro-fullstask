In the food court

Ramu hands the floor manager a card: "always have 3 counters serving masala chai from recipe v1.4". The manager places counters where there's space (scheduling), replaces any counter that collapses (self-healing), puts up one signboard that sends customers to whichever counters exist right now (Service), and when the card changes to v1.5, swaps counters one at a time so serving never stops (rolling update).

Common failures and their meaning

ImagePullBackOff: wrong image name/tag or no registry permission. CrashLoopBackOff: the app exits on start (config, missing secret, OOM). Pending: no node has the requested CPU/memory. Pod running but no traffic: readiness probe failing or Service selector doesn't match labels. Restarts under load: liveness probe too strict (checking the DB from liveness is a classic mistake).

Interview questions

What happens when you run kubectl apply for a Deployment?

The API server authenticates/authorises and validates the object and stores it in etcd. The Deployment controller creates/updates a ReplicaSet; the ReplicaSet controller creates Pod objects; the scheduler assigns each pod to a node with enough resources; that node's kubelet pulls the image and starts containers; probes mark them ready; endpoints are updated so the Service routes traffic to them.

Liveness vs readiness vs startup probes?

Startup: holds off the other probes until the app has booted (slow JVM start). Readiness: whether the pod should receive traffic; failing removes it from Service endpoints without restart. Liveness: whether the container is stuck and must be restarted; keep it to the process's own health.

Requests vs limits?

Requests are what the scheduler reserves and guarantees (placement and HPA utilisation are based on them). Limits are hard caps: CPU over the limit is throttled; memory over the limit gets the container OOMKilled. A common practice is memory request = limit, CPU limit unset or generous.
