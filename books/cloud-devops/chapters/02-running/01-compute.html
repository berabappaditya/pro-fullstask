Compute and autoscaling: VMs that grow and shrink with demand

Pick an instance type for the workload, run several copies behind a load balancer, and let an autoscaling group keep a metric (like CPU) near a target.

In the food court

On weekday afternoons Ramu runs 2 stoves; at 8 pm on Fridays, 10. He tells the food court: "keep each stove about 60% busy; light another if they're hotter, turn one off if they're idle; never fewer than 2, never more than 12." That rule is target-tracking autoscaling.

Scaling policies

target tracking
Keep a metric near a value

"Average CPU 60%" or "1,000 requests per instance". Simplest and usually best.

step scaling
Bigger alarm, bigger step

+1 at 70% CPU, +3 at 90%.

scheduled
Known peaks

Scale up at 7:45 pm before the IPL match, down at midnight.

predictive
Learn from history

Forecast daily patterns and scale ahead of them.

Things that bite

Warm-up time: a JVM instance takes 30–90 s to boot and get fast; scale on leading metrics and keep headroom. Statefulness: instances must be stateless (sessions in Redis, files in S3) or scale-in loses data. Health checks: the load balancer must stop sending traffic before an instance is terminated (connection draining / deregistration delay). Downstream limits: 10× instances = 10× DB connections.

Interview questions

Vertical vs horizontal scaling in the cloud?

Vertical: a bigger instance type (needs a restart, has a ceiling, single point of failure). Horizontal: more instances behind a load balancer with autoscaling (needs stateless design, gives availability). Databases often scale vertically first, then with read replicas and sharding.

How would you handle a known traffic spike, like a sale at 8 pm?

Scheduled scale-out ahead of time (instances warm, caches primed), raise max capacity, pre-warm or request LB capacity if needed, load-test beforehand, put a queue in front of non-urgent work, rate-limit and have a degraded mode. See the JioHotstar case study in the System Design book.
