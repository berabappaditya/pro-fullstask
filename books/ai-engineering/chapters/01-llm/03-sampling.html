Tokens, sampling, cost and latency

Temperature and top-p decide how the next token is picked from the probability list. Tokens decide what you pay and how long you wait.

Ramu's assistant

Asked to name today's special, a cautious assistant always says the most popular dish (temperature 0). A creative one sometimes suggests something unusual (high temperature). For writing invoices Ramu wants cautious; for Instagram captions, creative.

Cost and latency in practice

pricing
Per million tokens, input and output priced separately

Output tokens usually cost several times more than input. Reasoning models also bill their thinking tokens. Check your provider's current price list.

latency
Time to first token + tokens per second

Long prompts slow the first token; long outputs slow the end. Stream responses so users see progress.

prompt caching
Reuse a long static prefix

Providers cache repeated prompt prefixes (system prompt, tool definitions, documents) and charge much less for cached input. Put static content first.

batch
Asynchronous batch APIs

Large discounts for jobs that can wait hours (nightly classification).

model routing
Small model first

Route easy requests to a small, cheap model; escalate hard ones to a frontier model.

Lock it in

Cautious for invoices, creative for captions.

Low temperature = predictable, high = varied. Pay per input and output token; output costs more. Stream, cache static prefixes, cap max_tokens, route to smaller models.

Interview questions

Does temperature 0 make outputs deterministic?

Mostly but not fully: it picks the top token (greedy), but floating-point non-determinism on GPUs, batching and model updates can still change results. For reproducibility, pin the model version, log prompts and outputs, and design tests that tolerate variation (evaluate meaning, not exact strings).

How do you reduce LLM latency for a chat feature?

Stream tokens; shorten prompts (fewer, better retrieved chunks); prompt caching for static prefixes; smaller/faster models for simple turns; cap output length; parallelise retrieval and tool calls; cache whole answers for frequent questions (semantic cache); run close to users (regional endpoints).
