Tool calling: the model asks, your code acts

You describe functions (name, description, JSON schema); the model replies with a request to call one; your code runs it and sends the result back; the model writes the final answer. The model never executes anything itself.

Ramu's assistant

The assistant's phone has speed-dial buttons with labels: "check order status (needs order number)", "check stock (needs item, branch)". When a customer asks "where's my order 7?", the assistant presses the right button and reads out the result. He can't dial numbers that aren't on the buttons.

design
Good tools

Clear names and descriptions (the model reads them), few required parameters, enums over free text, idempotent where possible, small structured results.

safety
Your code is the gatekeeper

Validate arguments, authorise against the real user, rate-limit, require confirmation for destructive actions, log every call.

scale
Many tools

Dozens of tool definitions cost tokens and confuse selection. Group them, load relevant ones dynamically (tool search), or split across agents.

Lock it in

Labelled speed-dial buttons; the assistant presses, your phone dials.

Define tools (name + description + schema) → model emits a call → your code validates and executes → result back → final answer. Parallel calls are possible.

Interview questions

Does the LLM execute the function?

No. It only outputs a structured request (tool name + JSON arguments). Your application decides whether to execute it, with what permissions, and sends back the result. That's where validation, authorisation and auditing must live.

Tool calling vs structured output?

Both use JSON schemas. Structured output constrains the model's final answer format. Tool calling lets the model request actions or data mid-conversation and continue with the results; it's the basis of agents.
